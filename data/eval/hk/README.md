# Eval на датасетах организаторов

Набор вопросов к агенту по девяти CSV кейса (`gitverse.ru/kban/HK_Datasets`)
и сценариям 1–10 из README организаторов; сценарий 0 — «неудобные» вопросы
(технический критерий 8). Готовых ответов организаторы не дают, поэтому
эталоны считаем сами SQL-запросами по **сырым CSV**, мимо загрузчика агента:
ошибка загрузки тоже всплывёт как провал.

| Файл | Что в нём |
|---|---|
| `questions.yaml` | задачи: вопрос, таблица, проверки, пункты рубрики судьи |
| `gold.json` | эталонные значения, считает `scripts/eval_gold.py` |

## Запуск

Прогон и проверки — общий скрипт `scripts/eval.py` (`docs/eval.md`), эталоны —
`scripts/eval_gold.py`. Для `run_python` нужен рантайм песочницы
(`docs/sandbox.md`): без него тул скрыт от планировщика, и прогон не совпадает с
тем, что увидит жюри в docker.

```bash
make hk-data                                   # 9 CSV в data/hk_datasets и main.duckdb
python3 scripts/eval_gold.py                   # эталоны -> gold.json
python3 scripts/eval.py --questions data/eval/hk/questions.yaml \
  --columns-recall-only --repeat 3 --model ... # отчёт -> docs/reports/eval_*.md
```

`gold.json` берётся рядом с набором (`--gold` — другой файл). Каждая задача —
новая сессия, цепочка `follow_up_of` — одна сессия по порядку; `--ids` гоняет
задачи вместе с предками цепочки, `--repeat 3` — повторы для pass^k,
`--reply-to` — продолжения диалога отвечают на свой ход через `reply_to` (#173).
`--columns-recall-only` — `columns_all` этого набора не влияет на итог.

Ход, который провайдер отклонил с 429, помечается `api_error` и в оценку не
идёт — в отчёте есть строка «Исключено: ход сорван лимитом API провайдера».

## Формат задачи

```yaml
- id: sales-s6-channels-morph
  scenario: 6                       # 1–10 из README организаторов, 0 — неудобный
  dataset: t_01_prodazhi            # имя таблицы у агента
  follow_up_of: sales-s6-channels   # продолжение диалога в той же сессии
  question: "А теперь покажи то же самое в другом виде"
  expect: {chart_changed: true}     # детерминированные проверки
  judge: [follows_context]          # пункты рубрики судьи под задачу
  notes: "..."                      # эталонные факты для судьи и ревьюера
```

## Проверки (`expect`)

| Ключ | Проходит, если |
|---|---|
| — | ход дошёл до `done` (кроме сценария 0: там уточнение — нормальный исход) |
| `numbers.sql` | каждое число из результата SQL нашлось в ответе или таблице результата агента (допуск 0,5 %, `tolerance`, `tolerance_abs`; доля и процент считаются одним числом) |
| `numbers.any_of` | то же, достаточно одного варианта (выручка с возвратами и без) |
| `range.sql` | в тексте есть число из диапазона `[low, high]` — для прогнозов |
| `contains_any`, `contains_all`, `contains_any_groups`, `contains_any_sql` | в тексте есть подстрока (без регистра; `contains_all` — список групп, из каждой хоть одна) |
| `chart_any` | тип последнего графика из списка |
| `chart_changed` | тип графика сменился относительно прошлого хода |
| `dashboard` | пришло событие дашборда |
| `table_intact` | число строк исходной таблицы не изменилось |
| `columns_all` | с `--columns-recall-only` не влияет на итог: из него считается recall отбора колонок (#108) |

Числа агента берутся из текста ответа (`2 706 019 438 ₽`, `1,16 млрд`, `43 %`)
и из итоговой таблицы результата (`result_table` графика, первые 200 строк).
Полная семантика ключей — `docs/eval.md`.

## Судья

Каждому ответу с `done` судья ставит общие пункты — `answers_question`,
`grounded`, `business_readable` — и пункты задачи из `judge`. Тексты пунктов —
`GENERAL_RUBRIC` и `TASK_RUBRIC` в #181 (`scripts/eval/score.py`); судью переносят
в `scripts/eval_judge.py`, `scripts/eval.py` ключ `judge` принимает и не
проверяет. Судья видит вопрос,
справку по исходной таблице (строки, колонки, периоды), эталонные факты и
значения, ответ ровно в том виде, в каком его видит пользователь, и таблицу
результата; модель судьи не та же, что у агента. Задача решена, когда прошли все
проверки и все пункты судьи.

Один запуск судьи меняет вердикт пункта примерно в 14 % случаев (замер 25.10),
поэтому по умолчанию он оценивает ответ 3 раза (`--judge-votes`) и по каждому
пункту берётся большинство. Голос, на который судья не ответил (лимит, сбой),
отбрасывается; без единого голоса задача помечается «без оценки», а не провалом.

Перед тем как доверять судье, его надо сверить с ручной разметкой:
20–30 ответов, согласие по каждому пункту. Пункт с согласием ниже ~80 %
переписывается.
