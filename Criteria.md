# Сценарии и критерии

Сценарии и технические критерии — из README организаторов
([HK_Datasets](https://gitverse.ru/kban/HK_Datasets)). Ниже — как мы
проверяли каждый пункт и что получилось.

## Как проверяли

- **Живая проверка 31.10.2026** — ветка `dev` (`3e3c5b6`), платформа поднята
  через `docker compose up -d --build`, как в [README](README.md). Модель —
  `qwen/qwen3.8-27b` через OpenAI-совместимый API. Датасеты организаторов
  загружены в платформу сырыми CSV, вопросы заданы через тот же API, что и
  чат в интерфейсе. Эталоны посчитаны отдельно — SQL-запросами в DuckDB по
  сырым CSV.
- **Вопросы организаторов** (`questions.txt`): **5 из 6** верно, разбор каждого —
  [TestCases.md](TestCases.md).
- **Eval-набор** — 35 вопросов по девяти датасетам организаторов, все
  10 сценариев и «неудобные» вопросы (`data/eval/hk/questions.yaml`). Эталоны
  считаются по сырым CSV, ответ проверяют числа из эталона и LLM-судья.
  Последний прогон (31.10): **10 из 35** в обычном режиме, **14 из 35** в
  режиме «Проверка»; разбор — [docs/reports/eval_2026-10-31_verify.md](docs/reports/eval_2026-10-31_verify.md).
  Судья строгий: снимает балл, например, за техническое имя таблицы в ответе
  или за ответ без оговорки о неопределённости прогноза.

## Технические критерии

| # | Критерий | Статус | Как устроено и чем подтверждено |
|---|---|---|---|
| 1 | Прямое подключение к PostgreSQL или ClickHouse без предобработки | ✅ | «Подключение базы данных»: DuckDB читает таблицы источника напрямую (`postgres_scanner`, `clickhouse_scanner`), в режиме только чтения. Проверка 31.10: «Доставка» в PostgreSQL 16 и «Техподдержка» в ClickHouse 24.8, по 500 000 строк. Вопросы 4 и 3 организаторов на них дали те же ответы, что и на CSV: 0,964 дня (= 23,14 ч), «Собственная доставка»; 72,49 ч, «Доставка заказов» |
| 2 | Загрузка сырых CSV, все преобразования внутри платформы | ✅ | Все 7 CSV организаторов загружены как есть: BOM, разделитель `;`, десятичная запятая, пустые значения. Типы колонок, профиль и паспорт таблицы строятся автоматически при загрузке; вычисляемые колонки, фильтры и агрегаты агент делает внутри платформы |
| 3 | Описание структуры и содержимого простым языком, ответы по содержанию | ✅ | Сценарии 1–2 выше. Описание и названия колонок берутся из приложенного README датасета, если он есть, иначе их формулирует LLM |
| 4 | Визуализация по запросу в диалоге, вид подбирается и меняется по просьбе | ✅ | Сценарии 4 и 6 выше. Графики — Vega-Lite; вид меняется по просьбе («в другом виде», «круговой») или кнопкой на графике, без пересчёта |
| 5 | Дашборд генерируется автоматически и доступен повторно | ✅ | Сценарий 5 выше. Дашборд хранится на сервере (SQLite) и открывается из чата, из «Все дашборды» и по прямой ссылке `/dashboard/<id>`. Есть обновление данных, редактирование раскладки на канвасе, экспорт в PDF (деловой отчёт) и Excel (книга со сводкой и листом на каждую плитку) — подробнее в [README](README.md#экспорт) |
| 6 | Ответы и графики понятны бизнес-пользователю | ⚠️ | Ответ — заголовок с прямым ответом и числами, затем 3–5 пунктов «что и как посчитано». Оговорки ниже: технические имена в части мест |
| 7 | Память на уровне диалога | ✅ | Сценарий 6 выше. Сервер хранит ходы сессии и итоги расчётов (SQLite и DuckDB); вопрос можно задать «в ответ» на конкретное прошлое сообщение. Сессию можно передать коллеге ссылкой, файлом `.session` со всеми таблицами или рецептом без данных, который пересчитывается на данных получателя — подробнее в [README](README.md#сессию-можно-передать) |
| 8 | Некорректные и «неудобные» вопросы: уточнить, переформулировать, отклонить | ⚠️ | «Какая завтра погода в Москве?» — «Я отвечаю только по подключённым данным…». На неоднозначный вопрос агент задаёт уточнение с вариантами. Но на «Удали из таблицы все возвраты» агент не отказал, а посчитал таблицу без возвратов. Данные при этом не изменились: источники подключаются только на чтение, после хода в таблице те же 500 000 строк |
| 9 | Поднимается локально, без внешних закрытых систем | ✅ | `docker compose up -d --build` — два контейнера (backend, frontend), проверено на чистом клоне по [README](README.md). Модель — любой OpenAI-совместимый сервер, в том числе локальная Ollama или vLLM |
| 10 | Без облачных решений внутри, только open source | ✅ | Весь стек — open source: FastAPI, DuckDB, SQLite, Pyodide, Next.js, Vega-Lite, Ollama/vLLM, модель Qwen3.8-27B (открытые веса). Облачный API для модели — наш тестовый стенд, а не часть платформы: та же модель запускается локально в Ollama (`qwen3.8:27b`) или vLLM (`Qwen/Qwen3.8-27B`) |
| 11 | Интернет — только к определённым доменам и API, без поисковиков | ✅ | В работе backend обращается только к серверу модели (`LLM_BASE_URL`) и, если включены, к серверу эмбеддингов и реестру моделей Ollama. Пакеты Pyodide для песочницы скачиваются при сборке образа, в работе сеть ей не нужна. Код, который пишет LLM, выполняется в WASM-песочнице с отключёнными `fetch`, `WebSocket`, `XMLHttpRequest` и `pyodide.http`. Поисковых движков нет |

## Известные проблемы

Найдены при проверке 31.10, в порядке важности.

| Проблема | Где видно | Причина | Как исправить |
|---|---|---|---|
| Граница дня в вычисляемой колонке: «на конец 31 марта» превращается в `<= '2025-03-31'`, то есть в полночь начала дня | Вопрос 5 организаторов ([TestCases.md](TestCases.md)) | Для фильтров (`filter_rows`) дата без времени уже расширяется до конца дня; в выражениях `create_column` — ещё нет | Та же нормализация для выражений `create_column` |
| «Удали все возвраты» выполняется как фильтр, без объяснения, что данные только читаются | Технический критерий 8 | Планировщик воспринимает «удали» как «исключи из расчёта» | Отдельный маршрут для запросов на изменение данных: объяснить, что источник только читается, и предложить расчёт без возвратов |
| Вопрос о смысле поля иногда уходит в обзор таблицы | Сценарий 2 | Маршрут выбирает модель; обзор подходит для «что в таблице», но не для одного поля | Отдельный маршрут «описание колонки» из паспорта таблицы |
| В части мест видны технические имена: `t_01_prodazhi` в списке баз, `sum_Чистая выручка, руб.` в KPI-плитке | Сайдбар, дашборд | Название таблицы от LLM приходит позже загрузки; в плитке — имя колонки результата | Показывать название из паспорта; подписи KPI брать из заголовка плитки |
| Две столбчатые плитки дашборда («Доли каналов продаж», «Чистая выручка по категориям») показали подписи без столбцов | Дашборд из сценария 5 | Не разобрано | Проверить спецификацию этих плиток |
| Лаг между рядами считается по уровням, а не по приростам | Сценарий 9 | Инструмент кросс-корреляции берёт ряды как есть | Дифференцировать ряды перед корреляцией и добавлять оговорку «корреляция — не причинность» |
| Лента чата хранится в браузере | Сессия, открытая в другом браузере | Ход и результаты есть на сервере (`/api/sessions/<id>/bundle`), но интерфейс показывает ленту из localStorage | Восстанавливать ленту из бандла сессии |

## Модели

| Модель | Как запускали | Что получилось |
|---|---|---|
| **Qwen3.8-27B** (`qwen/qwen3.8-27b`) — рекомендуемая | OpenAI-совместимый API | 5 из 6 вопросов организаторов (31.10). На пяти самых трудных вопросах eval-набора: 11 из 15 ходов верно с рассуждением против 3 из 15 без него (28.10) |
| Nemotron-3-Nano 30B-A3B | OpenRouter | Планирует хорошо, но ошибается в выводе (ряд схлопывается в одно число); после правок промпта вывода — лучше (25.10, [docs/reports/llm_perf/dialog_and_insight_25-10.md](docs/reports/llm_perf/dialog_and_insight_25-10.md)) |
| Qwen2.5-Coder 7B | Ollama на CPU | Планирует плохо: не те инструменты и аргументы. Ход на CPU — 4–17 минут ([docs/reports/llm_perf/experiment_log.md](docs/reports/llm_perf/experiment_log.md)) |
| GigaChat-2 | API | Не подошёл: function calling отклоняет объекты без `properties`, аргументы шагов плана приходят пустыми |

Ограничение жюри — модель до 70B параметров. Qwen3.8-27B в него укладывается
и запускается на одной видеокарте от 24 ГБ.
