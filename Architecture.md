## Текущая архитектура

```
 Браузер ── Next.js (frontend, :3000) ── /api/* ──► FastAPI (backend, :8000) ──► LLM (OpenAI-совместимый API:
   чат, канвас, дашборды                                    │                     Ollama / vLLM / облако)
                                                            │
                     ┌──────────────────────────────────────┼────────────────────────────┐
                     ▼                                      ▼                            ▼
             Источники данных                     Агентный цикл хода              Хранилище
             CSV ─► DuckDB (таблица)              triage → planner → шаги         DuckDB: таблицы, паспорта,
             PostgreSQL ─┐ DuckDB читает          → проверки → insight           результаты шагов
             ClickHouse ─┴ напрямую (read-only)   → график → дашборд              SQLite: сессии, ходы, дашборды
                                                     │
                                                     ▼
                                     Реестр инструментов (SQL-шаблоны, статистика,
                                     временные ряды) + WASM-песочница (Pyodide)
                                     для кода, который пишет LLM
```

### Один ход диалога

1. **Маршрут (triage).** Small talk, обзор таблицы, смена вида графика без LLM,
   ответ на уточнение или план.
2. **Планировщик (LLM).** Получает вопрос, паспорт таблицы, отобранные под вопрос
   колонки и контекст сессии; возвращает `ResearchPlan` — шаги из реестра
   инструментов с аргументами, итоговый график, план дашборда. Ответ модели
   строго по JSON-схеме.
3. **Исполнитель шагов.** Каждый шаг — SQL в DuckDB поверх источника или
   прошлого шага; результат — временная таблица `temp_result_vN`. Ошибка шага →
   планировщик чинит шаг по тексту ошибки (до 2 раз) → уточняющий вопрос
   пользователю. Нет подходящего инструмента → код на Python в WASM-песочнице.
4. **Проверка (режим «Проверка»).** Проверки шагов и LLM-критик ответа:
   вердикт `ok`, дополнить план, переписать вывод, перепланировать.
5. **Вывод (LLM).** Заголовок с прямым ответом и числами, пункты «что и как
   посчитано», ограничения. Числа берутся только из результата шагов.
6. **График.** Выбор шага, вида и колонок (LLM, запасной путь — правила) →
   спецификация Vega-Lite. Смена вида — из кэша результата, без LLM.
7. **Дашборд (по запросу).** Плитки из шагов плана, хранятся на сервере со
   снимками данных; обновление данных, раскладка на канвасе, экспорт PDF/XLSX.

Все этапы стримятся во фронтенд событиями SSE: прогресс шагов, текст вывода
по мере генерации, графики, дашборд.

### Данные и память

- **Паспорт таблицы** — при подключении источника строятся профиль колонок
  (типы, пропуски, распределения, период) и описание простым языком. Названия
  и смысл колонок берутся из приложенного README датасета, иначе их пишет LLM.
- **Отбор колонок** — в промпт идут колонки, релевантные вопросу, а не вся
  схема: так широкие таблицы помещаются в контекст модели.
- **Связи таблиц** — объявленные ключи источника, затем эвристики; агент сам
  переходит к другой таблице, если вопрос про неё.
- **Память сессии** — ходы, планы и итоги расчётов на сервере; вопрос «в ответ»
  на конкретное сообщение; выгрузка сессии в файл и открытие на другой машине.

### Стек

| Слой | Технологии |
|---|---|
| Frontend | Next.js 14, React 18, TypeScript, Zustand, Tailwind CSS, Vega-Lite (react-vega), ECharts, react-grid-layout |
| Backend | Python 3.11, FastAPI, Pydantic, Instructor, OpenAI SDK, SSE |
| Данные | DuckDB (CSV, `postgres_scanner`, `clickhouse_scanner`), SQLite |
| Песочница | Node.js + Pyodide (WASM), pandas, numpy, scipy, statsmodels |
| Экспорт | ReportLab (PDF), openpyxl (XLSX) |
| LLM | Qwen3.8-27B через OpenAI-совместимый API: Ollama, vLLM или облачный провайдер |
| Поставка | Docker Compose: backend и frontend, опционально Ollama (CPU/GPU) и демо-PostgreSQL/ClickHouse |

### Почему так

| Решение | Зачем |
|---|---|
| DuckDB — единый движок | Один SQL-диалект для CSV, PostgreSQL и ClickHouse; источник читается напрямую, без ETL |
| План из инструментов, а не свободный SQL | Проверяемые шаги с понятными аргументами; модель до 70B надёжнее собирает план из готовых блоков, чем пишет SQL целиком |
| Свободный код — только в WASM-песочнице | Кодогенерация для того, чего нет в реестре, без доступа к сети и файловой системе хоста |
| Числа в выводе — только из результатов шагов | Модель пересказывает посчитанное, а не придумывает |
| Смена вида графика без LLM | «Покажи в другом виде» — за секунды |
| Любой OpenAI-совместимый сервер | Одна и та же платформа работает с локальной моделью в замкнутом контуре и с внешним API |

## Идеальная архитектура

Что мы сделали бы при большем времени и для промышленной эксплуатации.

- **Модель рядом с данными.** vLLM на GPU-сервере в контуре заказчика с
  Qwen3.8-27B; отдельная маленькая модель для маршрутизации и коротких
  ответов, большая — только для плана и вывода. Ход за секунды, а не минуты.
- **Семантический слой.** Метрики и измерения бизнеса («чистая выручка»,
  «конец дня», «просрочка») описаны один раз и переиспользуются агентом,
  а не выводятся из вопроса заново.
- **Проверка ответа всегда.** Детерминированные проверки шагов (границы дат,
  знаменатели долей, фильтры по статусам) и сверка итоговых чисел до показа
  ответа.
- **Пушдаун в источник.** Тяжёлые агрегаты считаются в самом PostgreSQL или
  ClickHouse, в DuckDB приходят только результаты.
- **Многопользовательский режим.** Аутентификация, права на источники и
  дашборды, PostgreSQL вместо SQLite для метаданных, общие дашборды команды.
- **Наблюдаемость.** Трассировка каждого хода (OpenTelemetry), оценка качества
  на eval-наборе в CI при каждом изменении промптов и инструментов.
