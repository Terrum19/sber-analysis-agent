# Журнал проверок гипотез (ночь 23.10.2026)

Фокус — логика и архитектура агента (structured output, парсинг, промпты, структура вызовов в ходе), а не настройка под конкретное железо.

**Стенд (постоянный для всех вариантов):** Ollama `qwen2.5-coder-32k-t14` (та же модель + `num_thread 14`, чтобы прогоны укладывались в ночь), `LLM_TIMEOUT_S=1800`, датасет `demo_events.csv`, 7 вопросов `scripts/llm_bench/questions/demo_events.txt`. Все вызовы LLM пишет прокси → `scripts/llm_bench/results/<вариант>/calls.jsonl`.

Формат записи: что проверял → как → результат (скорость / качество) → вывод.

## П1. Отбор тулов под вопрос (H-R1) — офлайн, без LLM

**Что:** в промпт планировщика вместо всех 40 тулов — ядро из 9 (filter_rows, group_by, time_bucket, sort_limit, aggregate, create_column, select_columns, describe_stats, search_categorical_values) + тулы, у которых имя/описание пересекается с вопросом по 5-буквенным основам (`bench_structured.topk_tools`, тот же приём, что `semantic_select` для колонок).
**Как:** реальный промпт планировщика из лога, подстановка 7 вопросов набора + 3 контрольных (сезонность, прогноз, сравнение групп).

| Метрика | Все тулы | Отбор |
|---|---|---|
| Символов в промпте | 12 127 | 4 955–6 695 (×1.8–2.4 меньше) |
| Тулов | 40 | 9–16 |
| Нужные тулы сохранились | — | 7/7 вопросов набора |

Доменные тулы находятся: «тренд» → trend_analysis, forecast; «сезонность» → seasonality, seasonal_decompose; «прогноз» → forecast; «различается… между регионами» → anova_one_way. Шум: частые основы («средн», «месяц») тянут лишние cohort/funnel-тулы; «выбросы» не находит ничего сверх ядра (ок — describe_stats в ядре).

**Влияние:** скорость — prefill пропорционален длине промпта, ожидаем ×~2 на каждом вызове планировщика (проверка на LLM — П3). Качество — риск потерять нужный тул при перефразировке; лечится эмбеддингами вместо основ или «добором» тулов при переспросе (если план невалиден из-за отсутствия тула — показать полный список).
**Вывод:** гипотеза жизнеспособна; дешёвая реализация по аналогии с `semantic_select`.

## П2. Что происходит с ответом в режиме instructor TOOLS (H-P0) — по логам прокси

**Что:** как текущий `LLMClient.complete_structured` (instructor 1.3.2, Mode.TOOLS) обрабатывает реальные ответы Qwen2.5-Coder через Ollama.
**Как:** логи `results/v1_tools_t14_aborted*/calls.jsonl`, `results/v1_mixed_oldprocess/calls.jsonl` (вопрос «Какая общая сумма amount?»).

| Вызов | Запрос | Ответ модели | prompt tok | сек |
|---|---|---|---|---|
| план | tools: ResearchPlan | текст: ```json {"steps":[{"tool":"aggregate",…}]}``` — корректный план | 4230 | 176–221 |
| план, fallback-1 | tools: Response (list) | тот же план текстом | 4307 | 172 |
| инсайт | tools: Insight | текст с JSON | 1016 | 43 |
| инсайт, fallback-1 | tools: Response (list) | текст с JSON | 1084 | 242 |

Во **всех** записанных вызовах модель ни разу не вернула tool_call — только текст с JSON. instructor требует ровно один tool_call и бросает ответ; fallback-1 с другой схемой даёт тот же текст и тоже выброшен; парсит текст только fallback-2 (3-й полный вызов).

**Влияние:** скорость — каждый structured-вызов стоит 3 вызова LLM вместо 1 (план: ~550 с вместо ~180 с; инсайт: ~300+ с вместо ~45 с); KV-кеш между попытками не помогает, т.к. описание tools вставляется шаблоном в начало system-промпта. Качество — не страдает (ответ в итоге разбирается), но ход длится в ~3 раза дольше; при таймауте клиента (120 с по умолчанию) — падает целиком.
**Вывод:** H-P0 подтверждена. Минимальная правка: при отсутствии tool_calls разбирать `message.content` уже полученного ответа (толерантным парсером, П-модуль `structured.py`). Архитектурно правильнее — H-P1: не полагаться на function calling у локальных моделей, просить JSON по схеме (`response_format=json_schema`, грамматика на стороне сервера) — проверка в V2.

## П3. Базовая линия V1 — текущий код целиком (`results/v1_tools_t14`)

**Что:** полный цикл `scripts/run_full_llm_cycle.py` без изменений логики (instructor TOOLS + fallback-цепочка), 7 вопросов.
**Как:** `run_variant.sh v1_tools_t14 LLM_MODEL=qwen2.5-coder-32k-t14 LLM_TIMEOUT_S=1800`; эталон — SQL по CSV напрямую (DuckDB).

**Скорость:** 7/7 ходов `done`, всего 5151 с (**в среднем 736 с на ход**, 625–867). Вызовов LLM: 44 = 1 check + 21 план + 21 инсайт — ровно **3 вызова на каждый structured-ответ** (П2 подтверждена на всех ходах). План ≈ 179 с/вызов (4270 ток prompt), инсайт ≈ 73 с/вызов. Время LLM — 99.9% хода.

**Качество (сверка с эталоном):**

| Вопрос | Агент | Эталон | |
|---|---|---|---|
| Общая сумма amount | 187 | 271 050 | ❌ |
| Событий по месяцам | «8 событий за год» | 12 мес × ~41 | ❌ |
| Средняя сумма по месяцам | янв 602, фев 647, апр 550 | янв 631, фев 603, апр 549 | ❌ |
| Топ-5 пользователей | u062 3970, u086 3910 … | совпадает | ✅ |
| Событий с суммой > 150 | 48 из 54 | 471 из 500 | ❌ |
| Выбросы в amount | «нет» | 0 по IQR | ✅ (вывод), статистика не та |
| Тренд выручки | «небольшой рост» | не проверено | ? |

**Итог: 2/6 проверяемых верно.** Причины ошибок — не парсинг, а логика:
1. **Инсайт считает по обрезанной выборке** (Q5): `InsightGenerator` отдаёт LLM `to_records(limit=50)` без общего числа строк; результат фильтра 471 строка → модель «посчитала» 50 показанных. → **H-Q1**.
2. **Обманчивое имя тула** (Q1): `aggregate` = частоты значений (value_counts), а скалярного агрегата по всей таблице в реестре нет (`group_by.by` обязателен). Модель выбрала тул по имени. → **H-T1**.
3. **Группировка по дате вместо периода** (Q2, Q3): «по месяцам» → `group_by(by=[event_date])` (84 дня) вместо `time_bucket(interval=month)`; Q2 к тому же SUM вместо COUNT. Пример в промпте показывает только group_by. → **H-T2**.
4. Инсайт без числа в заголовке («Общая сумма amount») — промпт не требует числа в headline. → **H-Q2**.

Эталон для «тренда» (дописано): помесячная выручка U-образная — 26 484 (янв) → 19 362 (авг) → 24 867 (дек), corr(выручка, время) = −0.40. Ответ V1 «небольшой тренд роста» — ❌.

- Вывод про тренд: модели нужен посчитанный тренд (наклон/корреляция или trend_analysis), а не глазомер по 12 числам — расширение H-Q1 на «факты о динамике».
