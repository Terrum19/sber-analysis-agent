# Гипотезы улучшения LLM-цикла агента: логика и архитектура

**Рабочая копия:** `sber-demo` (ветка `feature/console-demo`), изменения **не закоммичены**
**Дата:** 23.10.2026
**Подробный журнал проверок (что сделано → как повлияло):** [`experiment_log.md`](experiment_log.md)

## Коротко

На 7 вопросах к `demo_events.csv` (эталон посчитан SQL по CSV) цепочка прототипов дала:

| Вариант | Что включено | Время прогона | Вызовов LLM | Верных ответов |
|---|---|---|---|---|
| V1 | текущий код | 5151 с | 44 | 2/7 |
| V2 | + structured output через `json_schema` (H-P1/P2/P4) | 1635 с (×3.2) | 16 | 2/7 |
| V3 | + факты для инсайта, итог `group_by(by=[])`, `time_bucket` для периодов (H-Q1/Q2/T1/T2) | 1824 с | 18 | 4/7 |
| V4 | + валидация аргументов до выполнения (H-V1), проверка чисел (H-Q3), рамка контекста (H-C1) | 1680 с | 18 | 4.5/7 |
| V5 | + прошлые шаги только для вопросов-продолжений (H-C1b), отбор тулов (H-R1) | **984 с (×5.2)** | 17 | **5.5/7** |

**Итог: прогон в 5.2 раза быстрее, верных ответов 5.5 из 7 против 2.** Модель и железо одни и те же, менялась только логика агента.

**Ограничения выборки:** 7 вопросов, одна таблица, одна модель (Qwen2.5-Coder 7B, Q4), по одному прогону на вариант. Повтор V5 воспроизвёл все 7 ответов, время колебалось на ~13% (журнал, П8). Это сигнал о направлении, а не статистика. Стенд: Ollama на CPU, `num_thread` подобран под машину, чтобы прогоны помещались в ночь. Эта настройка одинакова для всех вариантов и к гипотезам не относится.

## Гипотезы по приоритету

### 1. Structured output: не полагаться на function calling у локальной модели

**H-P1 — `response_format=json_schema` вместо instructor TOOLS.** *Подтверждено (V1→V2: ×3.2 по времени, 44→16 вызовов).*
Qwen через Ollama **ни разу** не вернул tool_call: только текст с JSON в ```-блоке. instructor 1.3.2 требует ровно один tool_call и выбрасывает ответ. Fallback-1 (`list[Schema]`) получает тот же текст и тоже его выбрасывает, разбирает текст только fallback-2. Итого 3 полных вызова на каждый план и каждый инсайт. Схема, переданная грамматикой на сервер (Ollama/vLLM), даёт ответ с первого раза: за V2–V5 на ~50 вызовов не понадобилось ни одного переспроса из-за формата.
Прототип: `llm_structured_mode=json_schema` (`config.py`), `LLMClient._complete_json_schema`.

**H-P2 — толерантный разбор вместо выбрасывания.** *Дефект подтверждён тестами.*
Текущий `_extract_json_block` теряет валидный JSON со скобкой внутри строки, висячей запятой или `None`/`True`. Хуже того, ответ-список и оборванный ответ он **молча** превращает в пустой план (`ResearchPlan` из шага → `steps=[]`, pydantic игнорирует лишние поля). Агент тогда говорит «подходящих инструментов нет».
Прототип: `app/core/llm/structured.py` и 18 тестов в `tests/unit/test_llm_structured.py`. Заодно: `agent/parser.py` (`parse_steps`) нигде не вызывается — это мёртвый код.

**H-P4 — переспрос с текстом ошибки, а не смена режима.** Переспрос дописывается в конец промпта, поэтому префикс остаётся в KV-кеше и переспрос стоит десятки секунд (`plan_fix` 21–44 с против 170–180 с полного вызова). Смена режима (tools → list → json) меняет system-промпт с первого токена и каждый раз платит полный prefill.

### 2. Факты считает SQL, а не LLM

**H-Q1 — инсайт получает посчитанные факты о всей таблице результата.** *Подтверждено (V3).*
`InsightGenerator` отдавал модели `to_records(limit=50)` без общего числа строк. На вопрос «сколько событий > 150» модель пересчитала показанные строки: «48 из 54» (правильно 471). Теперь SQL считает число строк и сумму/среднее/мин/макс числовых колонок, к этому добавлена пометка «показано 50 из N».
Ещё один эффект: инсайт стал быстрее (медиана 62 → 33–44 с), потому что результаты теперь агрегированы и промпт короче.

**H-Q2 — в headline обязателен ответ числом.** До правки заголовки вида «Общая сумма amount» без числа.

**H-Q3 — детерминированная сверка чисел ответа с фактами.** *Механизм есть, в прогонах не срабатывал.* В V3 модель переписала верное 471 из фактов как «468». Числа в headline, которых нет в промпте, вызывают один дешёвый переспрос. Полезно и для больших моделей, но эффект пока не измерен.

**H-Q4 (не проверена) — факты о динамике.** На вопрос о тренде модель делает вывод на глаз по 12 числам: «рост», «уменьшается каждый месяц», «−10%», хотя на деле ряд U-образный, corr = −0.40. Наклон, корреляцию со временем и экстремумы по периодам стоит отдавать готовыми, как в H-Q1.

### 3. Реестр тулов: имена и семантика должны вести модель к верному выбору

**H-T1 — итог по всей таблице и честное имя `aggregate`.** *Подтверждено (V3: «общая сумма» 187 → 271 050).*
`aggregate` на деле считает частоты значений (value_counts), а тула «один итог по таблице» не было: у `group_by` аргумент `by` обязателен. Модель выбрала тул по имени. В прототипе `group_by(by=[])` даёт итог, к описанию `aggregate` добавлено «это НЕ сумма». Правильнее переименовать `aggregate` → `value_counts` и завести явный скалярный агрегат.

**H-T2 — периоды через `time_bucket`.** *Подтверждено (V3: «по месяцам» больше не группируется по 84 дням).* Пример в `STEP_PLANNER` показывает только `group_by`, его модель и копирует. Помогли правило и пример с `time_bucket`.

**H-V1 — все семантические ограничения аргументов — в `Args`-валидаторах.** *Подтверждено (V3→V4: `step_fix` 123 с → `plan_fix` 27 с).*
`time_bucket(function=AVG)` без `metric_column` проходил `validate_plan` и падал только при выполнении. После падения шёл дорогой `step_fix` с другим промптом. Перенос проверки в `TimeBucketArgs` (без флага, та же ошибка, только раньше) превращает это в дешёвый переспрос плана. Тот же аудит стоит провести по всем тулам.

### 4. Контекст планировщика: меньше, но точнее

**H-R1 — в промпт только релевантные тулы.** *Подтверждено по скорости (V4→V5: промпт плана 4284 → 2301 токенов, вызов плана ×2).*
40 тулов занимают ~80% промпта планировщика, а prefill линейно зависит от длины. Прототип: ядро из 9 тулов плюс совпадения по основам слов, по аналогии с `semantic_select` для колонок. Офлайн все нужные тулы сохраняются в 7/7 вопросов (П1). **Но на вопросе о тренде отбор изменил выбор модели**, и это воспроизвелось на повторе (П8): с полным списком она брала `time_bucket`, с урезанным берёт `revenue_analysis` без `date_column` и теряет динамику. Поэтому по умолчанию включать только после проверки на большем наборе. Как снизить риск: эмбеддинги вместо основ слов; полный список при переспросе; валидация «вопрос про время → в плане должна быть колонка даты».

**H-V2 (новая, П8) — отклонять неизвестные имена аргументов с подсказкой.** Модель пишет `column` вместо `metric_column`, лишний аргумент тихо игнорируется, и ошибка всплывает позже и дороже. Если отвечать «неизвестный аргумент column, возможно metric_column», будет дешёвый переспрос плана, как в H-V1.

**H-C1b — прошлые шаги сессии только для вопроса-продолжения.** *Подтверждено (V5: «выбросы» впервые посчитаны по всем данным).*
`SessionMemory.summary` — плоский список «шаг 0: purpose» всех прошлых ходов, без самих вопросов. Планировщик копировал оттуда фильтр «> 150» в независимый вопрос. **Инструкция «не повторяй» (H-C1, V4) не помогла.** Помогло структурное решение: не показывать прошлые шаги, если в вопросе нет признаков продолжения. В проде лучше определять продолжение явно (UI-кнопка «уточнить» или классификатор), а в summary хранить пары «вопрос → итог».

### 5. Устойчивость цикла

**H-L1 — таймаут и повторы.** *Подтверждено логами до этой работы.* При `llm_timeout_s=120` и встроенных повторах openai запрос планировщика дважды умирал по таймауту и начинался заново. Ollama брошенный запрос не отменяет и держит очередь. Варианты: стриминг с таймаутом между токенами (заодно прогресс в SSE); без повтора на timeout; `llm_max_tokens` (сейчас генерация не ограничена).

**H-L2 (не проверена) — маршрутизатор простых вопросов.** «Общая сумма X», «сколько строк», «X по месяцам» укладываются в шаблонный план без вызова планировщика. Это минус 90–180 с на ход, и в таких ответах нет места ошибке модели.

**H-L3 (не проверена) — инсайт без LLM для результата в одну ячейку.** Ответ «Общая сумма — 271 050» строится шаблоном.

## Как воспроизвести

```bash
cd sber-demo
# база (текущий код)
scripts/llm_bench/run_variant.sh v1 LLM_MODEL=<модель> LLM_TIMEOUT_S=1800
# все прототипы
scripts/llm_bench/run_variant.sh v5 LLM_MODEL=<модель> LLM_TIMEOUT_S=1800 \
    LLM_STRUCTURED_MODE=json_schema LLM_MAX_TOKENS=1024 \
    AGENT_QUALITY_FIXES=true AGENT_TOOL_TOPK=true
# сводка вызовов LLM
python3 scripts/llm_bench/summarize_calls.py scripts/llm_bench/results/v5/calls.jsonl
```
