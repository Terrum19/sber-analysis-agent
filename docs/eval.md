# Eval агента

`scripts/eval.py` прогоняет набор вопросов `data/eval/questions.yaml` (формат —
`data/eval/README.md`, #56) через оркестратор так же, как чат: каждый вопрос —
новая сессия над таблицей `dataset`, вопрос с `follow_up_of` — в сессии того
вопроса, на который он ссылается (таблица к ней привязывается один раз, при
создании, иначе `set_table` сбросил бы шаги прошлого хода). На уточнение
(`clarification_needed`) скрипт не отвечает: ход на этом заканчивается.

## Запуск

Таблицы набора — датасеты хакатона в DuckDB (`make hk-data`). Backend на время
прогона остановите: файл DuckDB открывает только один процесс.

```bash
make eval MODEL=qwen2.5-coder:7b     # модель по LLM_BASE_URL из окружения или .env
make eval EVAL_ARGS=--fake           # FakeLLM, модель не нужна
python3 scripts/eval.py --fake --per-scenario 1
python3 scripts/eval.py --model qwen2.5-coder:14b --ids sales-03 sales-04
```

| Параметр | Что делает |
|---|---|
| `--questions PATH` | набор вопросов, по умолчанию `data/eval/questions.yaml` |
| `--model NAME` | `LLM_MODEL` на время прогона и имя модели в отчёте |
| `--fake` | FakeLLM вместо модели (`USE_FAKE_LLM=true`), в отчёте модель `fake` |
| `--db PATH` | DuckDB с датасетами, по умолчанию `DUCKDB_PATH` |
| `--csv PATH...` | подключить CSV перед прогоном (с паспортом, как `POST /api/datasources`) |
| `--dataset TABLE` | задать всем вопросам одну таблицу |
| `--per-scenario N` | не больше N вопросов на сценарий; вопросы, на которые ссылается `follow_up_of`, добавляются |
| `--ids ID...` | только эти вопросы (и те, на которые они ссылаются) |
| `--out-dir PATH` | каталог отчёта, по умолчанию `docs/reports` |

С настоящей моделью скрипт сначала, как backend при старте, готовит её на сервере
Ollama (`LLM_PREPARE_MODEL`: скачивание, вариант с контекстом `LLM_NUM_CTX`), затем
узнаёт контекст сервера. Сессии прогона пишутся во временный каталог и в сайдбар
не попадают; результаты шагов (`temp_result_vN`) остаются в DuckDB и чистятся как
обычно.

Код выхода: 0 — прогон дошёл до отчёта; 1 — хотя бы один ход упал внутри скрипта
(ошибка оркестратора, а не провал проверки); 2 — модель не готова или DuckDB не
открылась. Проваленные проверки код выхода не меняют.

## Проверки

Каждый ключ `expect` — отдельная проверка; ключа нет (или он `null`) — проверки
нет. Вопрос прошёл, если прошли все его проверки. Ход, который упал или не дошёл
до `done` или `clarification_needed`, — провал `turn` с причиной.

| Ключ | Прошёл, если |
|---|---|
| `tools_any` | хоть один из инструментов есть среди выполненных шагов хода |
| `columns_all` | каждая колонка встречается в колонках или аргументах выполненных шагов: целым словом, без учёта регистра, в том числе внутри SQL |
| `value: {sql, tolerance}` | эталонный SQL выполнен в той же DuckDB, и каждое его число нашлось среди чисел `result_table` ответа (первые 1000 строк) с относительным допуском `tolerance` (0 по умолчанию) |
| `answer_contains` | каждая подстрока есть в `headline` или `details` ответа, без учёта регистра |
| `chart_type_any` | тип графика ответа (`usermeta.chart_type` спеки) из списка |
| `refusal` | ход отказался (`true`) или ответил (`false`). Отказ — событие `clarification_needed`, `error` или `refusal`, либо ход без шагов и без графика (ответ одним текстом); ответ с выполненными шагами без графика (`final_viz: "none"`) отказом не считается |

Шаги берутся у исполнителя (`StepExecutor.execute` в обёртке, поведение то же) и
из событий `progress` шагов. У провала всегда есть причина: какие инструменты и
графики были, каких колонок или подстрок нет, каких эталонных чисел нет в
`result_table`, текст ошибки или уточнения.

## Отбор колонок

Recall отбора — доля вопросов, у которых все `expect.columns_all` попали в
колонки, отобранные для планировщика. Считается по отбору, а не по шагам: модель
может ошибиться и при полном отборе. Отбор — результат `select_columns` в первом
вызове `StepPlanner.plan` хода (достройка плана после lookup-шага не считается);
без паспорта таблицы планировщик видит все колонки. Вопросы, где планировщик не
вызывался (small talk, обзор таблицы, смена вида графика), и вопросы без
`columns_all` в recall не входят. Средний размер блока колонок — длина того, что
идёт в промпт планировщика вместо `{columns}`: выжимка отобранных колонок и строка
остальных, в символах. Обе величины нужны для #108: замер до и после.

Отбор записывается без изменения планировщика: на время `plan` скрипт оборачивает
`select_columns`, `describe_columns` и `describe_other_columns` модуля
`app.core.agent.planner`. Если их переименуют, скрипт падает при запуске с
указанием, что обновить.

## Отчёт

`docs/reports/eval_<ГГГГ-ММ-ДД>_<модель>.md` (в имени модели всё, кроме
букв, цифр, `_`, `.` и `-`, заменяется на `-`: `qwen2.5-coder:7b` → `qwen2.5-coder-7b`) и
JSON с тем же именем рядом. В Markdown:

- общий pass %;
- таблица по сценариям: вопросов, прошло, %; сценарий 0 — неудобные вопросы;
- p50 и p95 времени до первого события хода и до его конца (`done` или
  `clarification_needed`), в секундах, ближайший ранг;
- recall отбора колонок и средний размер блока колонок;
- провалы: id, сценарий, таблица и причины по каждой проваленной проверке;
- предупреждение, если сервер LLM обрезал промпты (`prompt_truncated`): такой
  прогон для сравнения не годится.

JSON — те же итоги (`total`, `passed`, `pass_rate`, `scenarios`, `timing`,
`column_selection`, `prompt_truncated`) и `questions`: по каждому вопросу
проверки с причинами, `first_event_s`, `done_s`, чем кончился ход, инструменты,
отобранные колонки, размер блока колонок и `prompt_truncated`.

Отчёты прогонов на FakeLLM в git не кладём: FakeLLM на любой вопрос строит один и
тот же план, качество они не меряют.

## CI

`backend-ci.yml` (job `unit`) прогоняет набор на FakeLLM по вопросу на сценарий
над `data/sample_datasets/demo_events.csv` (`--dataset demo_events`), а отчёт кладёт
в summary запуска. Проверки там почти все проваливаются — шаг ловит только
поломку скрипта или формата набора. Пока `data/eval/questions.yaml` нет (#56), шаг
пропускается. `agent-smoke.yml` запускается только вручную, поэтому прогон
поставлен в `backend-ci.yml`: иначе скрипт ломался бы незаметно.
