# Eval агента

`scripts/eval.py` прогоняет набор вопросов `data/eval/questions.yaml` (формат —
`data/eval/README.md`, #56) через оркестратор так же, как чат: каждый вопрос —
новая сессия над таблицей `dataset`, вопрос с `follow_up_of` — в сессии того
вопроса, на который он ссылается (таблица к ней привязывается один раз, при
создании, иначе `set_table` сбросил бы шаги прошлого хода). На уточнение
(`clarification_needed`) скрипт не отвечает: ход на этом заканчивается.

Второй набор — `data/eval/hk/questions.yaml` (35 вопросов по девяти датасетам
организаторов, перенесён из #181) с эталонами `data/eval/hk/gold.json`; формат и
смысл вопросов — `data/eval/hk/README.md`. Эталоны считает
`scripts/eval_gold.py` по сырым CSV (`data/hk_datasets`), мимо загрузчика
агента: ошибка загрузки тоже всплывёт провалом. Ключи `judge` и `notes` вопроса
загрузчик принимает и не проверяет: они для LLM-судьи (`scripts/eval_judge.py`).

```bash
python3 scripts/eval_gold.py                    # эталоны -> data/eval/hk/gold.json
python3 scripts/eval.py --questions data/eval/hk/questions.yaml \
    --columns-recall-only --repeat 3 --model ...
```

## Тестовый конфиг

Все прогоны и eval команда делает на одном конфиге: `qwen/qwen3.8-27b` в
OpenRouter с выключенными размышлениями (строки — в `.env.example`):

```bash
LLM_BASE_URL=https://openrouter.ai/api/v1    # без /chat/completions: его добавит клиент
LLM_MODEL=qwen/qwen3.8-27b
LLM_API_KEY=...                              # ключ OpenRouter, не в git
LLM_REASONING_EFFORT=none
```

С размышлениями часть провайдеров OpenRouter (Near AI, Modal) ломает ответ по
`json_schema`: план приходит одной строкой в поле `tool`, и ход падает. В прогоне
#197 с размышлениями дошли до ответа 2 хода из 19, без них — все. Квантизация ни
при чём: DeepInfra (bf16) и ModelRun (fp4) давали 6 валидных планов из 6, Near AI
(fp8) — 0 из 6. Для локальных Ollama и vLLM флаг не нужен: они его не понимают, а
схему ответа держит сам сервер.

## Запуск

Таблицы набора — датасеты хакатона в DuckDB (`make hk-data`). Backend на время
прогона остановите: файл DuckDB открывает только один процесс.

```bash
make eval MODEL=qwen2.5-coder:7b     # модель по LLM_BASE_URL из окружения или .env
make eval EVAL_ARGS=--fake           # FakeLLM, модель не нужна
python3 scripts/eval.py --fake --per-scenario 1
python3 scripts/eval.py --model qwen2.5-coder:14b --ids sales-03 sales-04
```

| Параметр | Что делает |
|---|---|
| `--questions PATH` | набор вопросов, по умолчанию `data/eval/questions.yaml` |
| `--model NAME` | `LLM_MODEL` на время прогона и имя модели в отчёте |
| `--fake` | FakeLLM вместо модели (`USE_FAKE_LLM=true`), в отчёте модель `fake` |
| `--db PATH` | DuckDB с датасетами, по умолчанию `DUCKDB_PATH` |
| `--csv PATH...` | подключить CSV перед прогоном (с паспортом, как `POST /api/datasources`) |
| `--dataset TABLE` | задать всем вопросам одну таблицу |
| `--per-scenario N` | не больше N вопросов на сценарий; вопросы, на которые ссылается `follow_up_of`, добавляются |
| `--ids ID...` | только эти вопросы (и те, на которые они ссылаются) |
| `--out-dir PATH` | каталог отчёта, по умолчанию `docs/reports`; при `--fake` — новый временный каталог, чтобы отчёты FakeLLM не попадали в репозиторий |
| `--tag TAG` | суффикс имени отчёта: `eval_<дата>_<модель>_<tag>` (например, замер до и после #108) |
| `--force` | перезаписать отчёт с тем же именем; без него скрипт не запускается, если такой отчёт уже есть |
| `--gold PATH` | эталоны по id вопроса; по умолчанию `gold.json` рядом с набором, если он есть. Эталон из файла заменяет SQL проверки (`numbers`, `range`, `contains_any_sql`, `table_intact`); вопросов без эталона в файле это не касается. Эталон для id, которого нет в наборе, — ошибка загрузки |
| `--repeat N` | прогнать набор N раз подряд (у каждого повтора свои сессии); в отчёте pass^N — сколько вопросов прошли во всех повторах — и сколько хотя бы раз, в JSON `pass_k` — ещё и «прошёл k из N» по каждому вопросу. `total` и `passed` считают ходы всех повторов |
| `--judge` | LLM-судья по рубрике (раздел «Судья»): эндпоинт — `JUDGE_BASE_URL`, `JUDGE_MODEL`, `JUDGE_API_KEY`; без `JUDGE_BASE_URL` скрипт не запускается (код 2) |
| `--judge-votes N` | голосов судьи на ответ, по умолчанию 3 |
| `--reply-to` | продолжение (`follow_up_of`) отвечает на ход родителя: в `ChatRequest` уходит `reply_to` с `turn_id` из его `done` или `clarification_needed`. Работает после #173; пока в `ChatRequest` нет `reply_to`, скрипт предупреждает и идёт без него |
| `--columns-recall-only` | `columns_all` не проверяется, а только идёт в recall отбора колонок — так считает набор `data/eval/hk` (#181); без флага — проверка, как ниже |

Параллельного прогона (`--parallel` из #181) нет: файл DuckDB открывает один
процесс, а ходы одного процесса идут по очереди.

С настоящей моделью скрипт сначала, как backend при старте, готовит её на сервере
Ollama (`LLM_PREPARE_MODEL`: скачивание, вариант с контекстом `LLM_NUM_CTX`), затем
узнаёт контекст сервера. Сессии прогона пишутся во временный каталог и в сайдбар
не попадают; результаты шагов (`temp_result_vN`) остаются в DuckDB и чистятся как
обычно.

Код выхода: 0 — прогон дошёл до отчёта; 1 — хотя бы один ход упал внутри скрипта
(ошибка оркестратора, а не провал проверки); 2 — модель не готова, DuckDB не
открылась или отчёт с таким именем уже есть; 3 — у части вопросов не открылась
сессия (таблицы `dataset` нет в DuckDB: не загружены датасеты). Проваленные
проверки код выхода не меняют.

## Проверки

Каждый ключ `expect` — отдельная проверка; ключа нет (или он `null`) — проверки
нет; пустые `tools_any: []` и `chart_type_any: []` тоже не проверяются (обзор
таблицы и смена вида идут без плана); `columns_all` не проверяется у хода, где не
было ни шагов, ни вызова планировщика. Вопрос прошёл, если прошли все его
проверки. Провал `turn` с причиной:

- ход упал: исключение в скрипте или событие `error` (LLM недоступна, сбой этапа) —
  причина начинается с «ход упал:», в отчёте такие ходы считаются отдельно: это не
  оценка качества;
- ход не дошёл до `done` или `clarification_needed`;
- уточнение в сценарии 0 (неудобные вопросы) провалом хода не считается: там это
  нормальный исход, его оценивают `refusal` и судья (`refuse_or_redirect`);
- агент запросил уточнение (`clarification_needed`), а вопрос не ждёт отказа
  (`refusal` не `true`).

Видимый текст ответа для ключей из #181 (`numbers`, `range`, `contains_*`) — то,
что видит пользователь: `headline` и `details`, текст и варианты уточнения,
сообщение `error` и подписи графиков; подстроки — без учёта регистра, «ё» как
«е», пробелы схлопываются, но не обрезаются (`"0 "` требует пробела после нуля).
`answer_contains` по-прежнему смотрит только `headline` и `details`.

Ход, сорванный лимитом провайдера LLM (`api_error`: в исключении, ошибке этапа
`progress`, сообщении `error` или уточнении есть `Error code: 429`,
`rate_limit` или `concurrency_limit`), — не ответ агента: в проценты (общий, по
сценариям, pass^N) он не входит, в отчёте их число — строка «Исключено: ход
сорван лимитом API провайдера», в JSON — `api_errors` и `api_error` у вопроса.
Распознаётся по тексту ошибки: ход, где клиент сам повторил запрос после 429 и
дошёл до ответа, считается.

Типы в `expect` проверяются при загрузке набора: списки — только из строк (YAML
читает `[2023]` как число, `[NO]` как `false` — такие значения берите в кавычки),
`refusal`, `dashboard`, `chart_changed`, `table_intact` — `true` или `false`,
`contains_all` и `contains_any_groups` — списки непустых списков строк, у `value`,
`range` и каждого варианта `numbers` есть `sql`, `tolerance` и `tolerance_abs` —
числа не меньше 0, `judge` — список строк, `notes` — строка. Проверка, которая
упала с исключением, — провал этой проверки с текстом ошибки, прогон идёт дальше.

| Ключ | Прошёл, если |
|---|---|
| `tools_any` | хоть один из инструментов есть среди выполненных шагов хода |
| `columns_all` | каждая колонка встречается в колонках или строковых значениях аргументов выполненных шагов (не в именах аргументов): целым словом, без учёта регистра, в том числе внутри SQL, но не внутри строковых литералов `'…'` |
| `value: {sql, tolerance}` | эталонный SQL выполнен в той же DuckDB и вернул одно значение (одна строка, одна колонка; иначе — провал с причиной), и оно нашлось в ячейке `result_table` ответа (первые 1000 строк). Число — с относительным допуском `tolerance` (0 по умолчанию; при эталоне 0 допуск абсолютный), строка или дата — равенство без учёта регистра и пробелов по краям. Числовое совпадение не засчитывается, если в `result_table` больше 50 строк (`VALUE_MAX_ROWS`): в выгрузке сырых строк число находится случайно. Нет `result_table` (обзор таблицы) — эталон ищется в тексте ответа: числа с разделителями тысяч (пробел, U+00A0, U+202F) и запятой как десятичным знаком, строка — подстрокой |
| `answer_contains` | каждая подстрока есть в `headline` или `details` ответа, без учёта регистра; пробелы (в том числе неразрывные) схлопываются, «ё» считается «е» |
| `chart_type_any` | тип графика ответа (`usermeta.chart_type` спеки) из списка |
| `dashboard` | `true` — в ходе пришло событие `dashboard` (сценарий 5), `false` — не пришло |
| `numbers: {sql \| any_of, tolerance, tolerance_abs}` | каждое число эталона (все ячейки всех строк SQL или `numbers` из `gold.json`) нашлось среди чисел видимого текста ответа или ячеек `result_table` (первые 200 строк). `any_of` — список вариантов `{sql}`, достаточно одного, в котором нашлись все числа. Допуск относительный, `tolerance` (по умолчанию 0,005), или абсолютный, `tolerance_abs`; при эталоне 0 — точное совпадение. Доля и процент — одно число: эталон из `(0; 1]` ищется и умноженным на 100, из `(1; 100]` — и делённым на 100. Числа текста — с разделителями тысяч (пробел, U+00A0, U+202F), запятой или точкой в дробной части и множителями «тыс», «млн», «млрд», «трлн» |
| `range: {sql}` | в видимом тексте ответа есть число из `[low, high]`: SQL возвращает одну строку `low, high` (или `range` из `gold.json`). Для прогнозов; таблица результата не смотрится |
| `contains_any` | в видимом тексте есть хоть одна подстрока |
| `contains_all`, `contains_any_groups` | список групп подстрок; из каждой группы в видимом тексте есть хоть одна |
| `contains_any_sql` | в видимом тексте есть хоть одно значение первой колонки SQL (или `contains_any` из `gold.json`) |
| `chart_any` | тип **последнего** графика хода из списка (`chart_type_any` смотрит любой график) |
| `chart_changed` | `true` — у хода есть график и его тип не тот, что у последнего графика вопроса `follow_up_of`; `false` — не проверяется |
| `table_intact` | `true` — после хода в таблице `dataset` столько же строк, сколько в `row_count` из `gold.json`, а без эталона — сколько было перед ходом; `false` — не проверяется |
| `refusal` | ход отказался (`true`) или ответил (`false`). Отказ — событие `refusal` или ход без шагов и без графика (ответ одним текстом). Уточнение (`clarification_needed`) отказом не считается, в том числе шаблонное «Не удалось подобрать инструменты под этот вопрос» на пустой план: критерий жюри №8 ждёт объяснения и вариантов вопросов (#41); ответ с выполненными шагами без графика (`final_viz: "none"`) отказом не считается. Упавший ход (`error`) — ни отказ, ни ответ: проверка проваливается с причиной «ход упал» |

Шаги берутся у исполнителя (`StepExecutor.execute` в обёртке, поведение то же) и
из событий `progress` шагов. У провала всегда есть причина: какие инструменты и
графики были, каких колонок или подстрок нет, каких эталонных чисел нет в
`result_table`, текст ошибки или уточнения.

## Отбор колонок

Recall отбора — доля вопросов, у которых все `expect.columns_all` попали в
колонки, отобранные для планировщика. Считается по отбору, а не по шагам: модель
может ошибиться и при полном отборе. Отбор — результат `select_columns` в первом
вызове `StepPlanner.plan` хода (достройка плана после lookup-шага не считается);
без паспорта таблицы планировщик видит все колонки — такие вопросы в recall не
входят (иначе он равен 100 % по построению), их число пишется в отчёте. Вопросы, где планировщик не
вызывался (small talk, обзор таблицы, смена вида графика), и вопросы без
`columns_all` в recall не входят. Средний размер блока колонок — длина того, что
идёт в промпт планировщика вместо `{columns}`: выжимка отобранных колонок и строка
остальных, в символах. Обе величины нужны для #108: замер до и после.

Отбор записывается без изменения планировщика: на время `plan` скрипт оборачивает
`select_columns`, `describe_columns` и `describe_other_columns` модуля
`app.core.agent.planner`. Если их переименуют, скрипт падает при запуске с
указанием, что обновить.

## Судья

Детерминированные проверки не видят, понятен ли ответ и не выдумано ли в нём
что-то. Это оценивает LLM-судья — модуль `scripts/eval_judge.py` (перенесён из
#181). Включается флагом `--judge`. Пункты ответа: общие (`answers_question`,
`grounded`, `business_readable`, у сценария 0 — только `business_readable`) и
пункты вопроса из `judge`; в промпт идут вопрос, видимый текст ответа, первые 30
строк `result_table`, `notes` вопроса и, у продолжения, прошлый вопрос с ответом.
Каждый оценённый пункт — отдельная проверка `judge.<пункт>`: вопрос засчитан,
только если прошли и проверки, и судья. Неоценённые пункты (все голоса — сбой)
в итог не идут и перечислены в `judge_unrated`. В отчёте рядом с общим итогом —
строка «Без судьи, только проверки» (`checks_passed`, в JSON у вопроса —
`passed_checks`): верхняя граница, как «числа совпали» в #59. Ходы с `api_error`
судья не оценивает.

Модель судьи — отдельный OpenAI-совместимый эндпоинт, не тот, что у агента
(`LLM_BASE_URL`, `LLM_MODEL` судья не читает):

| Переменная | Что это | По умолчанию |
|---|---|---|
| `JUDGE_BASE_URL` | адрес эндпоинта (`.../v1`) | обязательна |
| `JUDGE_API_KEY` | ключ провайдера | `not-needed` |
| `JUDGE_MODEL` | модель судьи | `deepseek-flash` |

Судья вызывается с `temperature=0` и `response_format={"type": "json_object"}`,
таймаут 180 с.

Пункты рубрики — `RUBRIC` в модуле. Общие: `answers_question` (ответ на заданный
вопрос), `grounded` (числа и факты подтверждаются таблицей результата или
эталоном), `business_readable` (без SQL, внутренних имён таблиц и служебных
английских слов). Ходу, завершённому `done`, ставятся все три; в сценарии 0
(неудобные вопросы) — только `business_readable`. К ним добавляются пункты
задачи из её списка `judge` (`period_full`, `field_meaning`, `rate_vs_count`,
`refuse_or_redirect` и т. д.); набор пунктов хода собирает `rubric_points`.
Неизвестный пункт — ошибка до вызова судьи.

Судья видит вопрос, ответ ровно в том виде, в каком его видит пользователь
(пустой — «(пусто)»), первые 30 строк таблицы результата с общим числом строк
(без таблицы — оговорку, что числа сверяются с эталоном), эталонные факты задачи
(`notes`), по желанию — справку по исходной таблице и предыдущий ход диалога
(для `follows_context`), и тексты пунктов. Ответить он должен JSON
`{"items": {"<пункт>": {"pass": true|false, "why": "..."}}}`; ответ в блоке
кода или с текстом вокруг тоже разбирается.

Один запуск судьи меняет вердикт пункта примерно в 14 % случаев (замер в #181),
поэтому по умолчанию ответ оценивается 3 раза, и по каждому пункту берётся
большинство среди годных голосов; ничья — провал. Голос, который не разобран
(не JSON, нет `items`), вызов, упавший с ошибкой (лимит провайдера, сеть), и
пункт, которого нет в ответе судьи, в подсчёт не идут: это сбой судьи, а не
оценка ответа (как `api_error` у хода). Если годных голосов по пункту нет, пункт
не оценён: «пройден» — `null`, счёт `0/0`, причины — тексты сбоев. Судья не
роняет прогон. Результат по каждому пункту — пара «пройден, причины»: первая
причина — счёт голосов «за» из годных (`2/3`, `1/2`), дальше пояснения голосов,
совпавших с итогом.

Перед тем как доверять судье, его надо сверить с ручной разметкой: 20–30
ответов, согласие по каждому пункту; пункт с согласием ниже ~80 % переписывается.

## Отчёт

`docs/reports/eval_<ГГГГ-ММ-ДД>_<модель>.md` (в имени модели всё, кроме
букв, цифр, `_`, `.` и `-`, заменяется на `-`: `qwen2.5-coder:7b` → `qwen2.5-coder-7b`) и
JSON с тем же именем рядом. В Markdown:

- общий pass %;
- таблица по сценариям: вопросов, прошло, %; сценарий 0 — неудобные вопросы;
- p50 и p95 времени до первого события хода и до его конца (`done` или
  `clarification_needed`), в секундах, ближайший ранг;
- recall отбора колонок и средний размер блока колонок;
- провалы: id, сценарий, таблица и причины по каждой проваленной проверке;
- предупреждение, если сервер LLM обрезал промпты (`prompt_truncated`): такой
  прогон для сравнения не годится;
- число упавших ходов (событие `error`) и вопросов, у которых не открылась сессия;
- при `--repeat` больше 1 — pass^N и «хотя бы раз», у провалов — номер повтора;
- число ходов, исключённых как `api_error`.

JSON — те же итоги (`total`, `passed`, `pass_rate`, `scenarios`, `timing`,
`column_selection`, `prompt_truncated`, `errored`, `no_session`, `api_errors`,
`pass_k`) и `questions`: по каждому вопросу и повтору проверки с причинами,
`first_event_s`, `done_s`, чем кончился ход, инструменты, отобранные колонки,
размер блока колонок, `prompt_truncated`, номер повтора `repeat` и `api_error`.

Отчёты прогонов на FakeLLM в git не кладём: FakeLLM на любой вопрос строит один и
тот же план, качество они не меряют.

## CI

`backend-ci.yml` (job `unit`) прогоняет набор на FakeLLM по вопросу на сценарий
над `data/sample_datasets/demo_events.csv` (`--dataset demo_events`), а отчёт кладёт
в summary запуска. Проверки там почти все проваливаются — шаг ловит только
поломку скрипта или формата набора. Пока `data/eval/questions.yaml` нет (#56), шаг
пропускается. `agent-smoke.yml` запускается только вручную, поэтому прогон
поставлен в `backend-ci.yml`: иначе скрипт ломался бы незаметно.
