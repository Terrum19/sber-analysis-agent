# Визуализация (сценарии №4 и №6)

## Сборка спеки — `core/viz/vega_spec_builder.py`

`build_vega_spec(chart_type, result_table, db=None, data=None, titles=None, title=None,
x=None, y=None, color=None)` возвращает Vega-Lite v5 JSON, который фронт рисует
без серверной отрисовки.

- **Данные.** Если `data` не передан, строки выгружаются из `result_table`
  через `db.to_records(result_table, limit=500)` (`SPEC_ROW_LIMIT`). Значения
  приводятся к JSON: `date`/`datetime` -> ISO-строка, `Decimal` -> `float`,
  `NaN`/`inf` -> `null`, прочее -> строка.
- **Типы каналов** определяются по значениям колонки (пропуски не учитываются):
  даты и строки вида `2024-01`, `2024-01-05`, `2024-01-05 10:00` — `temporal`;
  числа (кроме булевых) — `quantitative`; остальное — `nominal`.
- **Заголовки осей** — из `titles` (колонка -> подпись). Оркестратор берёт их
  из паспорта таблицы сессии: `column_aliases()` читает словари `glossary` и
  `titles` (название колонки из описания таблицы, первая буква заглавная).
  Без названия — имя колонки; для счётчика — «Количество».

| Вид | mark | x | y | прочее |
|---|---|---|---|---|
| `bar` | bar | первая категория (дата — ordinal) | сумма первой метрики или count | |
| `line`, `area` | line / area | дата; иначе колонка с «порядковым» именем (year, month, год, месяц, …) как ordinal; иначе категория; иначе первая метрика | сумма метрики или count | color — категория |
| `histogram` | bar | первая метрика, `bin: {maxbins: 20}` | count | |
| `scatter` | point | первая метрика | вторая метрика | color — категория |
| `box` | boxplot | категория (или одна общая коробка) | первая метрика | |
| `heatmap` | rect | первая категория | вторая категория | color — сумма метрики или count |
| `table` | text | колонка (через `fold`) | номер строки | text — значение |
| `kpi` | `{type: text, fontSize: 48}` | — | — | text — первая метрика первой строки |

В каждом виде заполнен `tooltip`. Если данных не хватает (например, `scatter`
с одной числовой колонкой), строится ближайший подходящий вид: scatter/box/heatmap
-> bar, bar без категорий -> histogram, kpi без чисел -> table, без колонок
вовсе -> пустая таблица.

**Явные колонки** (`x`, `y`, `color` — выбор агента, см. ниже) заменяют
«первую категорию» и «первую метрику» из таблицы выше:

- `x` — ось любого типа: целочисленный ключ (`store_id`) на оси `bar`
  остаётся категорией (`nominal`), год числом на оси `line` — `ordinal`;
- `y` — число (у `heatmap` — вторая категория, число там в `color`);
- `color` — разбивка цветом: у `bar` столбцы серий стоят рядом (`xOffset`),
  у `line`/`area` — серии, у `scatter` — цвет точек. Если колонки названы,
  а `color` нет, график одной серией: категория сама в цвет не попадает.

Колонки, которой нет в данных, нет и в выборе. Названные колонки пишутся в
`usermeta` (`x`, `y`, `color`), и пересчёт плитки дашборда
(`dashboards/recalculate.py`) строит график по ним же.

**KPI.** Одно крупное число. В `data.values` лежит весь результат, а
`transform` оставляет только первую строку:

```json
{"mark": {"type": "text", "fontSize": 48},
 "transform": [{"window": [{"op": "row_number", "as": "_row"}]},
               {"filter": "datum._row == 1"}],
 "encoding": {"text": {"field": "total", "type": "quantitative", "title": "Выручка",
                       "format": ",.2~f"},
              "tooltip": [{"field": "total", "type": "quantitative", "title": "Выручка"}]},
 "title": "Выручка за квартал"}
```

Подпись плитки — `title` спеки; если заголовок не передан (например, при
морфинге), подписью становится название метрики. Метрика — первая
числовая колонка, её название — из `titles`. Число форматируется как
`,.2~f`: разделители разрядов, не больше двух знаков после запятой.
KPI рассчитан на результат из одной строки: при нескольких строках
показывается первая, а без `ORDER BY` в SQL их порядок не гарантирован.
Из KPI морфинг ведёт сначала в `table`, затем в `bar`.

## Выбор графика агентом — `core/agent/chart_pick.py`, `core/viz/chart_choice.py`

Вид и колонки графика выбирает модель — по готовым результатам, когда их
колонки и строки уже известны, а не при планировании, когда имён колонок
промежуточных таблиц ещё нет.

**Ответ в чате.** `ChartPicker.pick(question, steps, tables, final_viz)` описывает
модели таблицы всех выполненных шагов, кроме lookup (`CHART_STEP`: шаг,
`purpose`, тул и его вид, число строк, колонки с типом и числом уникальных
значений, первые 10 строк) и одним вызовом получает `AnswerChart`:

```json
{"step_id": 1, "chart_type": "bar", "x": "store_id", "y": "sum_revenue",
 "color": "category", "limit": null, "reason": "..."}
```

Модель видит и таблицу, по которой считался стат-тест, поэтому строка
`pearson_corr` в конце плана больше не превращает график в таблицу.
`final_viz` планировщика идёт в промпт подсказкой (`ANSWER_HINT`), явную
просьбу пользователя («таблицей», «линией») модель читает в вопросе.

Выбор проверяет `rejection(choice, records)`: колонки есть в таблице шага,
`kpi` — только одно число, вид подходит к названным колонкам
(`fits_columns`: y — число; `bar` — не больше 30 значений x, иначе нужен
`limit`; `line` — от 3 значений x; `scatter` — два разных числа;
`histogram` — от 20 значений). Не подошло — один повтор с причиной
(`ANSWER_RETRY`), затем — прежний выбор `select_chart` (ниже). Он же
работает, если модель не ответила, если таблица шага одна и в ней не больше
строки (kpi или таблица — выбирать нечего), при `final_viz: "none"` и для
выборки под гистограмму распределения.

`limit` — топ-N строк по `y`: `top_rows` сохраняет их в новую
`temp_result_vN` (`ORDER BY y DESC NULLS LAST LIMIT N`), на неё ссылаются
график, смена вида и экспорт.

Выбор идёт задачей параллельно с инсайтом. Инсайт пишется по таблице
результата хода, а график может быть по другому шагу: результат хода для
следующих вопросов («из них…») не меняется.

**Плитки дашборда** выбираются так же (`CHART_CHOICE`, один вызов на все
плитки) и проверяются тем же `rejection`; `x`, `y`, `color` и `limit` идут в
спеку плитки. Список видов и ролей колонок у обоих промптов общий —
`CHART_KINDS`.

## Запасной выбор вида — `core/viz/chart_selector.py`

`select_chart(question, result_table, requested="auto", records=None)`:

1. `requested == "none"` -> `"none"`: графика не будет.
2. `records` из одной строки: одна числовая колонка с конечным значением
   (не NaN и не бесконечность) -> `kpi`, всё остальное (несколько чисел,
   подпись и число) -> `table`. Пустой результат -> `table`.
3. Кандидат — явный `requested` или эвристика по словам вопроса
   («распределение» -> histogram, «динамика»/«по месяцам» -> line,
   «сравни» -> bar, «связь»/«корреляция» -> scatter, по умолчанию bar).
4. Кандидат проверяется по данным: `fits(chart_type, records, types)`.
   Не подошёл -> `table`. Без `records` проверки нет, кандидат
   возвращается как есть.

`fits` (`types` — из `infer_field_types(records)`):

| Вид | Подходит, когда |
|---|---|
| `line`, `area` | не меньше 3 строк (`MIN_LINE_POINTS`) и упорядоченная ось X: колонка-дата или колонка с именем вроде `month`, `year`, `период` (`ordered_column`) |
| `scatter` | не меньше двух числовых колонок |
| `histogram` | одна числовая колонка или несколько, но одна из них названа в вопросе (`histogram_column`: по имени или по началу слов названия — «цен» из «Цена»); не меньше 20 значений в ней (`MIN_HISTOGRAM_VALUES`) |
| `bar` | есть категория (текст или дата) и в первой категории не больше 30 значений (`MAX_BAR_CATEGORIES`) |
| `box` | есть числовая колонка |
| `heatmap` | не меньше двух категорий |
| `kpi` | одна строка с одним конечным числом |
| `table` | всегда |

Планировщик выбирает вид в `final_viz` (`ResearchPlan.final_viz` принимает
только известные виды, `auto` и `none`, регистр не важен; на другое
значение instructor переспрашивает модель). `none` — ответ одной фразой,
графику нечего показать.

Оркестратор передаёт в `records` первые `SPEC_ROW_LIMIT` строк результата —
и для графика ответа, и для плиток дашборда: по ним `fits` проверяет вид.

## Заголовок графика

`title` спеки — название шага, чей результат показан (`purpose` шага
`result_step` или последнего выполненного). Если `purpose` пуст или
результат взят не из шага этого плана, заголовок собирает
`chart_title(records, titles)`: «{метрика} по {категории}» из названий
колонок (`titles`, иначе имена колонок; первая буква категории строчная),
только метрика, если категории нет, и «Количество по {категории}», если
нет метрики. Инсайт (`headline`) остаётся подписью под графиком
(`caption`), а плитка дашборда берёт `title` спеки.

## План дашборда — `core/agent/planner.py`

Плитка дашборда не несёт своего SQL: она ссылается на шаг плана
исследования, а данные берёт из его `temp_result_vN`. Поэтому плитки
составляет планировщик вместе с шагами — в `ResearchPlan`:

- `dashboard_title` — название дашборда;
- `template_id` — id шаблона (`core/dashboards/templates.py`), если план
  построен по шаблону;
- `dashboard_tiles` — список `DashboardTilePlan {title, step_id, chart_type,
  is_kpi, insight_needed}`: `step_id` — шаг, чей результат показывает
  плитка; `chart_type` — вид из списка `final_viz` или `auto`; `is_kpi` —
  плитка-число; `insight_needed` — к плитке нужен короткий вывод LLM.
  Непустой список плиток сам ставит `dashboard_requested = true`; `null`
  от модели читается как пустой список.

Вопрос про дашборд узнаётся по словам «дашборд», «панель», «сводка»
(`is_dashboard_question`, регистр не важен). Для такого вопроса к промпту
планировщика добавляется `DASHBOARD_PLAN` (`prompts/step_planner.py`):
формат плиток и правила (шаги под плитки — от `$source`, KPI — шаг с одной
строкой и одним числом, вывод — у одной-двух главных плиток). Дальше:

- `templates.match(columns, titles)` по всем колонкам таблицы (с названиями
  из паспорта) нашёл шаблон — в промпт идут его плитки как обязательные
  (название, вид, назначение) и найденные колонки ролей. Шаблон
  применяется всегда, что бы ни ответила модель: `dashboard_requested`
  ставится в `true`, плитки плана переписываются по
  шаблону детерминированно: порядок, `title`, `chart_type`, `is_kpi` и
  `insight_needed` — из шаблона, от модели берётся только `step_id`
  (плитка ищется по названию; по порядку — первая неиспользованная, но
  только если плиток у модели столько же, сколько в шаблоне; плитка
  шаблона без пары отбрасывается). Ставятся `template_id` и, если
  модель не дала название, `dashboard_title` = имя шаблона.
- Шаблона нет — модель сама составляет от 3 до 6 плиток, хотя бы одну KPI.

Номера шагов планировщик переписывает подряд с `next_step_id`; ссылки
плиток переписываются вместе с ними, если модель прислала шаги с
различными `step_id`.

`validate_plan` проверяет и плитки: `step_id` каждой — среди шагов плана
или уже выполненных; при `dashboard_requested` без плиток — ошибка
`NO_TILES` («добавь плитки или поставь dashboard_requested=false»), а
если план построен по шаблону и в нём нет хотя бы одной плитки шаблона
(`template_gap`) — `NO_TEMPLATE_TILES` с названиями недостающих плиток:
отказаться от дашборда по шаблону модель не может. Обе
ошибки уходят в переспрос, как ошибки шагов. Если после переспроса не
хватает только плиток шаблона, ход не обрывается: `template_id`
сбрасывается, остаются плитки, которые модель дала, а без плиток
дашборд собирается из графика ответа (см. «Сборка дашборда»). План, который кончается
lookup-шагом, будет достроен: плитки на ещё не составленные шаги
отбрасываются без переспроса, а отсутствие плиток ошибкой не считается.

## Сборка дашборда — `core/agent/orchestrator.py`

При `dashboard_requested` ход отдаёт `text` и `chart` ответа как обычно
(инсайт по `result_step`), а затем собирает дашборд (`_build_dashboard`) и
шлёт событие `dashboard`. `Execution` несёт для этого `plan` и `tables`
(шаг -> `temp_result_vN`), их заполняет `_finish`. План, достроенный
после lookup-шага, сохраняет плитки, название и шаблон (новые плитки
заменяют прежние); состояние уточнения (`pending_recovery`) хранит их же,
так что после «пропустить шаг» дашборд строится по тому же плану.

Для каждой `DashboardTilePlan`:

- таблица — результат шага `step_id`; шаг не выполнился (пропущен при
  уточнении) — плитка выпадает;
- вид — `chart_type`, а при `auto` — `select_chart(title, table, records)`
  (у `is_kpi` с `auto` — `kpi`). KPI строится только по одной строке с
  одним числом: иначе вид выбирается заново как для `auto`, а в лог
  пишется предупреждение; спека — `build_vega_spec(..., title=title)`;
- вывод — `InsightGenerator.generate_tile_insight(title, table, chart_type)`
  только при `insight_needed`: промпт `TILE_INSIGHT`, `llm.complete`, первые
  30 строк результата, ответ в 1–2 предложения. Остальные плитки LLM не
  вызывают; сбой LLM оставляет плитку без вывода;
- `DashboardTile(source_step_id, result_table, spec, insight, is_kpi)`;
  `is_kpi` — построенный вид `kpi`. Плитка, которая не
  собралась (ошибка спеки), выпадает с записью в лог.

Раскладка на сетке в 12 колонок (`_arrange`): KPI — первыми рядами, по
`w=3, h=2` (четыре в ряд), графики — под ними по два в ряд, `w=6, h=4`.
Плитки в дашборде идут в том же порядке: сначала KPI, затем графики.

`DashboardGenerator(db).generate(session_id, title, tiles, template_id)`
снимает данные плиток (`snapshot_data`) и сохраняет дашборд в SQLite;
название — `dashboard_title` плана или «Дашборд», `template_id` — из плана.
Если ни одной плитки не собралось (план без плиток — например, старое
состояние уточнения), дашборд, как раньше, состоит из одной плитки с
графиком и инсайтом ответа, без `template_id`. Сбой сборки — событие
`progress` `dashboard/failed`, затем `done`: ответ и график уже отданы.

## Событие `dashboard` — `api/schemas/chat.py`

`DashboardPayload {dashboard_id, title, tiles: DashboardTileOut[]}`.
`DashboardPayload.from_dashboard(dashboard)` копирует плитки без
`snapshot_data` (в SSE оно `null`): данные уже лежат в
`spec.data.values`. Полный дашборд со снимками отдаёт
`GET /api/dashboards/{id}`. `stale` в событии всегда `false`: оно
вычисляется только при пересчёте.

`usermeta` (стандартное поле Vega-Lite для метаданных):

```json
{"chart_type": "line", "requested_type": "line", "result_table": "temp_result_v2",
 "columns": [{"field": "month", "title": "Месяц", "type": "temporal"}]}
```

`chart_type` — фактически построенный вид; по нему работают морфинг и фронт.
Имена колонок с `.`, `[`, `]` экранируются в `field` (`field_ref`).

## Смена вида без LLM — `core/viz/chart_morph.py`

- `detect_morph(question)` возвращает целевой вид, `"auto"` или `None`.
  Названный вид («таблицей», «линейным графиком», «гистограммой», «точечной»,
  «ящик с усами», «тепловой картой», «с заливкой», «столбчатой») засчитывается
  только вместе с глаголом перерисовки или отсылкой к прошлому ответу
  («сделай», «перестрой», «замени», «в виде», «то же самое», «а теперь», …),
  поэтому «Построй гистограмму распределения суммы» остаётся новым вопросом.
  «В другом виде», «по-другому», «другой график», «смени тип графика» — `"auto"`.
- `morph(current_type, to_type, data, titles=None, result_table=None)`:
  явно названный вид строится как есть; для `"auto"` берётся первый вид из
  `MORPH_MAP[current_type]`, который на этих данных отличается от текущего.

## Оркестратор — `core/agent/orchestrator.py`

1. Если `detect_morph()` распознал смену вида и в `SessionMemory` есть
   `last_chart()`, строки берутся из кешированной `temp_result_vN` через
   `StateCache.get(table, limit=500)`, спека перестраивается `morph()`, в поток
   уходят события `chart` и `done`. Планировщик, шаги и `InsightGenerator`
   не вызываются; в DuckDB выполняется только `SELECT * FROM temp_result_vN LIMIT 500`.
2. Если прошлого графика нет или temp-таблица пропала (`duckdb.Error`), ход
   идёт обычным путём: планировщик -> шаги -> инсайт и выбор графика
   агентом (параллельно) -> `build_vega_spec` -> `record_chart()`. Если
   агент не выбрал график, строки результата (до 500) читаются один раз и
   идут и в `select_chart`, и в спеку.
3. Вид для `select_chart`: `final_viz` плана; результат analysis- или
   lookup-шага — `table`, кроме ряда по времени, который подходит для `line`
   (`trend_analysis`, `seasonal_decompose`): он рисуется линией (`area`,
   если её просили). По оси Y — первая числовая колонка (`value`); `p_value`,
   `yoy_change` и другие колонки тренда идут в инсайт, а не на график. Разрез
   `by` — цвет линии. При `final_viz:
   "none"` событий `progress` этапа `chart` и `chart` нет, `last_chart()`
   не меняется, ход заканчивается `text` и `done`. Если при этом попросили
   дашборд, `none` не действует: вид выбирается как для `auto`.
4. Исключение для распределения: если показан результат `describe_stats`,
   а в вопросе есть «распредел» или «гистограмм» (`asks_distribution`),
   график строится по самой колонке. В новую `temp_result_vN` идут её
   непустые значения — случайные 500 (`USING SAMPLE reservoir`,
   `REPEATABLE (0)`), а не первые 500 строк. Вид — `histogram`, заголовок —
   `purpose` шага, таблица статистик уходит в инсайт как сопутствующая. Если
   непустых значений меньше 20 (`MIN_HISTOGRAM_VALUES`) или выборка не
   собралась (ошибка пишется в лог), показывается таблица статистик.
5. Гистограмма по результату с несколькими числовыми колонками строится по
   колонке из вопроса: она сохраняется в новую `temp_result_vN`, и график,
   смена вида и дашборд ссылаются на неё.

## Фронтенд — `components/charts/ChartRenderer.tsx`

- `usermeta.chart_type == "table"` -> HTML-таблица по `data.values`
  с заголовками из `usermeta.columns`;
- `renderer == "echarts"` (опция в `option`) или объект с `series` без `$schema`
  -> `echarts-for-react` (только на клиенте);
- иначе -> Vega-Lite (`react-vega`), ширина по контейнеру.
