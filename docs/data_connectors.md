# Подключение источников данных

Требование: подключение к CSV / PostgreSQL / ClickHouse **без предварительной
обработки** — вся трансформация внутри платформы после загрузки.

## Унификация через DuckDB

Все коннекторы (`backend/app/core/data/connectors/`) реализуют один интерфейс
`BaseConnector.connect(db) -> list[str]` и создают таблицы/представления в
DuckDB. Дальше весь аналитический слой работает в **едином диалекте SQL**,
не зная, откуда пришли данные.

| Коннектор | Механизм | Статус |
|---|---|---|
| `csv.py` | кодировка + `sniff_csv` + `read_csv` -> TABLE (копия в DuckDB) | готов |
| `postgres.py` | `postgres_scanner` + `ATTACH ... (TYPE postgres, READ_ONLY)` -> TEMP VIEW | готов |
| `clickhouse.py` | чтение через HTTP/clickhouse ext | TODO(round-2) |

Коннектор выбирается фабрикой `connectors/factory.py::build_connector(kind, dsn, schema)`.

## CSV

Технический критерий №2: сырые CSV «в исходном и произвольном виде». Файл сохраняется
как есть, все преобразования делает платформа после загрузки. Рассчитано на типичные
российские выгрузки: cp1251, разделитель `;`, десятичная запятая, пробелы в разрядах,
даты `дд.мм.гггг`.

### API

`POST /api/datasources/csv` — `multipart/form-data`, поле `files` (один или несколько
файлов: таблицы связываются по идентификаторам, поэтому их удобно грузить вместе):

```bash
curl -F files=@Продажи.csv -F files=@users.csv http://localhost:8000/api/datasources/csv
```

```json
{"datasource_id": "csv_1a2b3c4d5e", "kind": "csv", "tables": ["prodazhi", "users"], "profile_summary": ""}
```

| Код | Когда |
|---|---|
| 200 | все файлы подключены |
| 400 | файл пуст или не читается как CSV (в `detail` — первая строка ошибки DuckDB) |
| 413 | файл больше `CSV_MAX_UPLOAD_MB` (по умолчанию 1024 МБ) |
| 422 | в запросе нет ни одного файла |

Загрузка атомарна: если хотя бы один файл не подключился, уже созданные таблицы
удаляются, а папка загрузки стирается. Файлы лежат в
`STORAGE_DIR/uploads/<datasource_id>/<таблица>.csv`.

### Как файл становится таблицей (`load_csv`)

1. **Имя таблицы** — из имени файла: транслитерация кириллицы, нижний регистр,
   `_` вместо прочих символов (`Продажи за 2024.csv` -> `prodazhi_za_2024`). Имя,
   начинающееся с цифры, получает префикс `t_`. Латинские имена таблиц проще для
   Text-to-SQL. Имена **колонок** не меняются.
2. **Кодировка.** BOM UTF-8/UTF-16 -> по нему; иначе файл потоково проверяется как
   UTF-8; если не декодируется — считается cp1251. Не-UTF-8 файл перекодируется в соседний
   `<имя>.utf8.csv`, оригинал не трогается. Расширение DuckDB `encodings` не
   используется: в замкнутом контуре его нельзя скачать.
3. **Разделитель** — `sniff_csv`. Если сниффер видит одну колонку (так бывает при «рваных»
   строках), разделитель берётся по частоте `;` `,` `\t` `|` в строке заголовка.
   Типы колонок и форматы дат (`%d.%m.%Y`, `%d.%m.%Y %H:%M:%S`) определяет DuckDB.
4. **Копирование в таблицу DuckDB** (`CREATE OR REPLACE TABLE ... AS SELECT * FROM read_csv(...)`) —
   единственный полный проход по файлу: ошибки формата далеко за выборкой сниффера
   всплывают при загрузке, а не в запросе агента. Затем по уже скопированной таблице
   считаются строки и текстовые колонки проверяются на «числа в русском формате».
   Всё это — одна транзакция: если режим чтения не подошёл, прежняя таблица с тем же
   именем остаётся нетронутой.
5. **Лестница режимов**, если проход упал:
   - строгое чтение;
   - `null_padding` + `strict_mode=false`: короткие строки дополняются NULL, лишние
     значения уходят в колонки `columnN`;
   - `all_varchar` + `ignore_errors`: все колонки текстом (например, в числовой колонке
     строка 300 000 содержит «нет данных»); приведение типов — уже в запросах
     через `TRY_CAST`. В лог пишется предупреждение с номером режима.
6. **Числа из текста.** Текстовая колонка становится `DOUBLE`, если *каждое*
   непустое значение — число вида `-1 234,56` / `1 234.5` / `0,5` и хотя бы одно
   содержит запятую или пробел-разделитель разрядов (обычный, неразрывный,
   узкий неразрывный). Условие «хотя бы одна запятая» защищает коды вроде `007`:
   их DuckDB оставляет текстом, и мы тоже. Колонка преобразуется в таблице
   (`ALTER TABLE ... ALTER ... TYPE DOUBLE USING TRY_CAST(...)`), исходный файл не переписывается.
7. **Таблица** постоянная (не TEMP), поэтому загруженные CSV переживают перезапуск API
   и не зависят от файла: после загрузки его можно удалить. CSV-таблица помечена
   комментарием `csv:<имя файла>` (`duckdb_tables().comment`). Повторная загрузка файла
   с тем же именем заменяет прежнюю CSV-таблицу (и CSV-представление, созданное прежней
   версией загрузчика); если имя занято таблицей или представлением другого источника,
   добавляется суффикс `_2`, `_3`, ...

   Почему копия, а не представление над `read_csv`: представление перечитывает и
   разбирает весь файл при каждом запросе. На `05_События_приложения.csv` из датасетов
   хакатона (1 млн строк, 223 МБ) группировка шла 1,2 с против 0,04 с по таблице,
   полный профиль — 22,7 с против 1,4 с. Все 9 датасетов (≈1,5 ГБ CSV) загружаются за
   ≈50 с и занимают ≈160 МБ в `main.duckdb`.

### Известные ограничения

- `1,234` читается как 1.234 (русская десятичная запятая), а не как английский разделитель тысяч.
- Кроме UTF-8/UTF-16 распознаётся только cp1251 (KOI8-R и пр. прочитаются как cp1251).
- Даты `дд/мм/гггг` и `мм/дд/гггг` различает DuckDB по данным; если все дни ≤ 12,
  выбор неоднозначен.
- Профилирование при загрузке и `profile_summary` ещё не подключены (см. ниже).
- Перекодированная копия `<имя>.utf8.csv` пишется рядом с исходным файлом. Для загрузок через API
  это папка `uploads/<datasource_id>/`; при прямом вызове `DuckDBManager.attach_csv` с cp1251-файлом
  копия появится в каталоге этого файла.
- При повторной загрузке файла с тем же именем старая папка `uploads/<прежний id>/`
  остаётся на диске; чистки загрузок пока нет.

## PostgreSQL

Пользователь передаёт строку подключения, платформа «подвешивает» таблицы
схемы к DuckDB как представления. Данные не копируются, база пользователя
не меняется: подключение только на чтение.

### API

`POST /api/datasources/db`:

```json
{"kind": "postgres", "dsn": "postgresql://analyst:***@db.local:5432/shop", "schema": "public"}
```

Ответ `200`:

```json
{"datasource_id": "pg_1a2b3c4d5e", "kind": "postgres", "tables": ["orders", "users"], "profile_summary": ""}
```

`datasource_id` стабилен для одного источника (хост, порт, база,
пользователь, схема) и не зависит от значения пароля.

| Код | Когда |
|---|---|
| 400 | некорректная строка подключения (`ValueError`) |
| 422 | неизвестный `kind` (валидация pydantic) |
| 501 | коннектор ещё не реализован (ClickHouse) |
| 502 | PostgreSQL недоступен или отклонил подключение (`PostgresConnectionError`) |
| 503 | в DuckDB нет расширения `postgres_scanner` (`PostgresExtensionUnavailableError`) |

Тексты ошибок — на русском и никогда не содержат пароль.

### Строка подключения

Модуль `connectors/pg_dsn.py` принимает два формата:

- URI: `postgresql://user:password@host:port/dbname?sslmode=require`
  (схема `postgresql://` или `postgres://`, спецсимволы в пароле — в
  percent-кодировке, например `@` -> `%40`);
- libpq «ключ=значение»: `host=db.local port=5432 dbname=shop user=analyst password='p w'`.

Проверки до любого обращения к сети (иначе `ValueError`): строка не пуста,
формат распознан, у URI поддерживаемая схема и корректный порт, кавычки
закрыты, **указан хост** (`host` или `hostaddr`). Если не задан
`connect_timeout`, подставляется 10 секунд — недоступный сервер не
подвешивает запрос.

Для логов и сообщений используется маскированная форма
`postgresql://analyst:***@db.local:5432/shop` (`PostgresDsn.masked()`,
`repr`/`str` коннектора и DSN).

### Последовательность `PostgresConnector.connect(db)`

1. `INSTALL postgres_scanner` — без сети может не выполниться; это не
   ошибка, если расширение уже установлено в образ.
2. `LOAD postgres_scanner` — если не загрузилось, расширения нет:
   `PostgresExtensionUnavailableError`. В замкнутом контуре расширение
   должно быть заранее установлено в образ бэкенда (issue-06).
3. Если в DSN есть пароль — `CREATE OR REPLACE TEMPORARY SECRET <alias>_secret (TYPE postgres, PASSWORD $password)`;
   пароль передаётся параметром запроса и не попадает в текст SQL.
4. `ATTACH 'host=... port=... dbname=... user=...' AS <alias> (TYPE postgres, READ_ONLY[, SECRET <alias>_secret])`.
5. `SELECT table_name FROM <alias>.information_schema.tables WHERE table_schema = $schema ORDER BY table_name`
   — в список попадают и таблицы, и представления PostgreSQL.
6. Прежнее подключение того же источника (если было) снимается: его view
   удаляются, база отсоединяется, секрет удаляется.
7. Пустая схема -> `[]` и `logging.warning`. Больше `POSTGRES_MAX_TABLES`
   таблиц (по умолчанию 50, `.env`) -> берутся первые по алфавиту,
   `logging.warning`.
8. На каждую таблицу — `CREATE OR REPLACE TEMP VIEW "<имя>" AS SELECT * FROM <alias>."<схема>"."<таблица>"`.
9. `logging.info`: источник (без пароля), число таблиц, время подключения.

После этого запрос `SELECT * FROM orders` работает так же, как для CSV.

### Решения и их причины

**Пароль — только в секрете DuckDB.** Строка из `ATTACH` видна любому SQL
через `duckdb_databases()` и повторяется в текстах ошибок libpq. Поэтому
`ATTACH` получает строку без пароля, а пароль лежит во временном секрете
(в `duckdb_secrets()` он показан как `redacted`). Секрет должен жить, пока
база подключена: расширение открывает новые соединения по мере надобности.
Секрету нужна именно строка «ключ=значение»: с URI DuckDB не может
объединить параметры секрета — поэтому URI всегда переводится в этот вид.

**Новый алиас на каждое подключение.** Алиас — `pg_<хеш источника>_<случайный
токен>`. Прежнее подключение того же источника снимается только после того,
как новое успешно открылось и вернуло список таблиц. Неудачная попытка
(например, с неверным паролем) не ломает рабочий источник.

**Временные представления (TEMP).** `ATTACH` не сохраняется в файле
`main.duckdb`, а обычный `VIEW` сохранился бы и после перезапуска ссылался
на исчезнувшую базу. TEMP-представления живут, пока открыто соединение,
поэтому после перезапуска источник нужно подключить заново (повторный
`POST /api/datasources/db`).

Ограничение: временные объекты DuckDB видны **только в том соединении**, в
котором созданы. Сейчас `DuckDBManager` держит одно соединение на всё
приложение (`app.state.db`), и это работает. Если в будущем появятся
`cursor()`/отдельные соединения на сессию, подключать источник нужно в том
же соединении, где выполняются запросы.

**Конфликт имён.** Если имя таблицы уже занято другим объектом DuckDB
(например, CSV `events` или таблицей из другой базы), представление
получает имя `<dbname>_<таблица>`, затем `<алиас>_<таблица>`, затем
`<алиас>_<таблица>_<N>`. Сравнение без учёта регистра, как в DuckDB. О
переименовании пишется `logging.warning`; итоговые имена — в `tables`
ответа.

**Экранирование.** Имена схем и таблиц всегда в двойных кавычках (таблица
`"Mixed Case"` работает), имя схемы в запрос к `information_schema`
передаётся параметром.

**Потоки.** Обработчик `/api/datasources/db` синхронный — FastAPI выполняет
его в пуле потоков, подключение к PostgreSQL не блокирует цикл событий.
`DuckDBManager.query/execute` и вся последовательность `connect()`
выполняются под `DuckDBManager.lock`.

**Большие схемы.** Проверено на схеме из 1500 таблиц (локальный
PostgreSQL 17): подключение с лимитом 50 занимает около 0,4 с, повторное — около
0,1 с. Лимит отбирает первые таблицы в лексикографическом порядке
(`t1, t10, t100, ...`), а не «самые важные».

### Известные ограничения

- Расширение `postgres_scanner` устанавливается при сборке образа бэкенда
  (`backend/Dockerfile`), поэтому в контейнере коннектор работает без сети. При запуске
  без Docker и без сети расширение нужно установить заранее, иначе — 503.
- После перезапуска бэкенда источники PostgreSQL нужно подключить заново:
  строки подключения не сохраняются (и не должны храниться с паролем в файле).
- У `DUCKDB_PATH` относительный путь по умолчанию (`backend/storage/...`): при запуске
  из `backend/` или в Docker (`WORKDIR /app`, том `/app/storage`) файл базы окажется
  не там, где ожидается. Теперь `DuckDBManager` открывается при старте приложения,
  поэтому путь стоит задавать явно через `.env`.

### Сообщения об ошибках

| Причина (по тексту ошибки libpq) | Сообщение |
|---|---|
| неверный пользователь/пароль | «PostgreSQL отклонил учётные данные…» |
| хост не найден | «Не удалось найти хост PostgreSQL…» |
| отказ в соединении, таймаут, нет сети | «Сервер PostgreSQL недоступен…» |
| базы/пользователя нет | «Указанная база данных или пользователь не существует…» |
| нет прав | «Недостаточно прав для чтения схемы PostgreSQL.» |
| прочее | «Не удалось подключиться к PostgreSQL.» |

К сообщению добавляется маскированный источник. Исходный текст ошибки
(без пароля) пишется в лог на уровне `WARNING`.

## Профилирование при подключении

`core/data/profiling.py` считает по колонкам: NaN%, min/max, медиана,
квартили, std. `core/data/schema_enrichment.py` отдаёт схему LLM для
генерации алиасов (с учётом бизнес-словаря). Результат — «паспорт данных»
(память уровня 3), на основе которого строится описание «что передо мной».
