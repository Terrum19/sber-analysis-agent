# Подключение источников данных

Требование: подключение к CSV / PostgreSQL / ClickHouse **без предварительной
обработки** — вся трансформация внутри платформы после загрузки.

## Унификация через DuckDB

Все коннекторы (`backend/app/core/data/connectors/`) реализуют один интерфейс
`BaseConnector.connect(db) -> list[str]` и создают таблицы/представления в
DuckDB. Дальше весь аналитический слой работает в **едином диалекте SQL**,
не зная, откуда пришли данные.

| Коннектор | Механизм | Статус |
|---|---|---|
| `csv.py` | кодировка + `sniff_csv` + `read_csv` -> TABLE (копия в DuckDB) | готов |
| `postgres.py` | `postgres_scanner` + `ATTACH ... (TYPE postgres, READ_ONLY)` -> TEMP VIEW | готов |
| `clickhouse.py` | `clickhouse_scanner` + `ATTACH` -> TEMP VIEW в DuckDB | готов |

Коннектор выбирается фабрикой `connectors/factory.py::build_connector(kind, dsn, schema)`.

## CSV

Технический критерий №2: сырые CSV «в исходном и произвольном виде». Файл сохраняется
как есть, все преобразования делает платформа после загрузки. Рассчитано на типичные
российские выгрузки: cp1251, разделитель `;`, десятичная запятая, пробелы в разрядах,
даты `дд.мм.гггг`.

### API

`POST /api/datasources/csv` — `multipart/form-data`, поле `files` (один или несколько
файлов: таблицы связываются по идентификаторам, поэтому их удобно грузить вместе):

```bash
curl -F files=@Продажи.csv -F files=@users.csv http://localhost:8000/api/datasources/csv
```

```json
{
  "datasource_id": "csv_1a2b3c4d5e",
  "kind": "csv",
  "tables": ["prodazhi"],
  "profiles": [
    {
      "table": "prodazhi",
      "rows": 2,
      "columns": 2,
      "period_from": "2024-02-01",
      "period_to": "2024-03-15",
      "description_status": "none",
      "summary": null,
      "warnings": [
        "Файл в кодировке cp1251 перекодирован в UTF-8.",
        "Числа, записанные текстом, приведены к числам в колонках «Сумма»."
      ]
    }
  ]
}
```

`profiles` — сводка паспорта по каждой таблице (`TableBrief`, тот же ответ
у `POST /api/datasources/db`):

| Поле | Смысл |
|---|---|
| `table`, `rows`, `columns` | имя таблицы, число строк и колонок из профиля |
| `period_from`, `period_to` | `min_date`/`max_date` первой `temporal`-колонки профиля (ISO 8601) или `null`, если дат нет |
| `description_status` | перенос описания в паспорт: `none` — описания нет, LLM не вызывается; `pending` — фоновый перенос запущен; `ready` — перенесено; `failed` — LLM не разобрала документ хотя бы по одной колонке (у неё `fingerprint = NULL`) или перенос упал. В ответе подключения статус `none` или `pending`, итог читается из паспорта |
| `summary` | описание таблицы «что передо мной» от LLM, если оно уже построено по этим же данным (повторное подключение), иначе `null`: новое описание строится в фоне после переноса описания колонок (`ingest.summarize`, см. [memory.md](memory.md#что-передо-мной--coredataoverviewpy)) |
| `warnings` | что загрузчик CSV исправил или не смог исправить: перекодировка, числа из текста, нестрогий разбор, загрузка всех колонок текстом с отбрасыванием нечитаемых строк. У источников БД пусто |

`GET /api/datasources/tables` по-прежнему возвращает список имён (`string[]`):
фронт уже использует этот контракт.

`GET /api/datasources/tables/{table}` — тот же `TableBrief` по паспорту
таблицы: итоговый `description_status` (`ready` / `failed`) и `summary`,
когда фоновая задача их построила (`404`, если паспорта нет). `warnings`
здесь всегда пустой: предупреждения загрузчика в паспорте не хранятся и
приходят только в ответе подключения.

| Код | Когда |
|---|---|
| 200 | все файлы подключены |
| 400 | файл пуст или не читается как CSV (в `detail` — первая строка ошибки DuckDB) |
| 413 | файл больше `CSV_MAX_UPLOAD_MB` (по умолчанию 1024 МБ) |
| 422 | в запросе нет ни одного файла |

Загрузка атомарна: если хотя бы один файл не подключился, уже созданные таблицы
удаляются, а папка загрузки стирается. Файлы лежат в
`STORAGE_DIR/uploads/<datasource_id>/<таблица>.csv`.

### Как файл становится таблицей (`load_csv`)

1. **Имя таблицы** — из имени файла: транслитерация кириллицы, нижний регистр,
   `_` вместо прочих символов (`Продажи за 2024.csv` -> `prodazhi_za_2024`). Имя,
   начинающееся с цифры, получает префикс `t_`. Латинские имена таблиц проще для
   Text-to-SQL. Имена **колонок** не меняются.
2. **Кодировка.** BOM UTF-8/UTF-16 -> по нему; иначе файл потоково проверяется как
   UTF-8; если не декодируется — считается cp1251. Не-UTF-8 файл перекодируется в соседний
   `<имя>.utf8.csv`, оригинал не трогается. Расширение DuckDB `encodings` не
   используется: в замкнутом контуре его нельзя скачать.
3. **Разделитель** — `sniff_csv`. Если сниффер видит одну колонку (так бывает при «рваных»
   строках), разделитель берётся по частоте `;` `,` `\t` `|` в строке заголовка.
   Типы колонок и форматы дат (`%d.%m.%Y`, `%d.%m.%Y %H:%M:%S`) определяет DuckDB.
4. **Копирование в таблицу DuckDB** (`CREATE OR REPLACE TABLE ... AS SELECT * FROM read_csv(...)`) —
   единственный полный проход по файлу: ошибки формата далеко за выборкой сниффера
   всплывают при загрузке, а не в запросе агента. Затем по уже скопированной таблице
   считаются строки и текстовые колонки проверяются на «числа в русском формате».
   Всё это — одна транзакция: если режим чтения не подошёл, прежняя таблица с тем же
   именем остаётся нетронутой.
5. **Лестница режимов**, если проход упал:
   - строгое чтение;
   - `null_padding` + `strict_mode=false`: короткие строки дополняются NULL, лишние
     значения уходят в колонки `columnN`;
   - `all_varchar` + `ignore_errors`: все колонки текстом (например, в числовой колонке
     строка 300 000 содержит «нет данных»); приведение типов — уже в запросах
     через `TRY_CAST`. В лог пишется предупреждение с номером режима.
6. **Числа из текста.** Текстовая колонка становится `DOUBLE`, если *каждое*
   непустое значение — число вида `-1 234,56` / `1 234.5` / `0,5` и хотя бы одно
   содержит запятую или пробел-разделитель разрядов (обычный, неразрывный,
   узкий неразрывный). Условие «хотя бы одна запятая» защищает коды вроде `007`:
   их DuckDB оставляет текстом, и мы тоже. Колонка преобразуется в таблице
   (`ALTER TABLE ... ALTER ... TYPE DOUBLE USING TRY_CAST(...)`), исходный файл не переписывается.
7. **Таблица** постоянная (не TEMP), поэтому загруженные CSV переживают перезапуск API
   и не зависят от файла: после загрузки его можно удалить. CSV-таблица помечена
   комментарием `csv:<имя файла>` (`duckdb_tables().comment`). Повторная загрузка файла
   с тем же именем заменяет прежнюю CSV-таблицу (и CSV-представление, созданное прежней
   версией загрузчика); если имя занято таблицей или представлением другого источника,
   добавляется суффикс `_2`, `_3`, ...

   Почему копия, а не представление над `read_csv`: представление перечитывает и
   разбирает весь файл при каждом запросе. На `05_События_приложения.csv` из датасетов
   хакатона (1 млн строк, 223 МБ) группировка шла 1,2 с против 0,04 с по таблице,
   полный профиль — 22,7 с против 1,4 с. Все 9 датасетов (≈1,5 ГБ CSV) загружаются
   `make hk-data` за ≈15 с вместе с профилем (Apple M4, 10 ядер, 16 ГБ RAM, DuckDB 1.5.6)
   и занимают ≈160 МБ в `main.duckdb`.

### Известные ограничения

- `1,234` читается как 1.234 (русская десятичная запятая), а не как английский разделитель тысяч.
- Кроме UTF-8/UTF-16 распознаётся только cp1251 (KOI8-R и пр. прочитаются как cp1251).
- Даты `дд/мм/гггг` и `мм/дд/гггг` различает DuckDB по данным; если все дни ≤ 12,
  выбор неоднозначен.
- Перекодированная копия `<имя>.utf8.csv` пишется рядом с исходным файлом. Для загрузок через API
  это папка `uploads/<datasource_id>/`; при прямом вызове `DuckDBManager.attach_csv` с cp1251-файлом
  копия появится в каталоге этого файла.
- При повторной загрузке файла с тем же именем старая папка `uploads/<прежний id>/`
  остаётся на диске; чистки загрузок пока нет.

## PostgreSQL

Пользователь передаёт строку подключения, платформа «подвешивает» таблицы
схемы к DuckDB как представления. Данные не копируются, база пользователя
не меняется: подключение только на чтение.

### API

`POST /api/datasources/db`:

```json
{"kind": "postgres", "dsn": "postgresql://analyst:***@db.local:5432/shop", "schema": "public",
 "description": "## orders\n- amount — сумма заказа"}
```

`description` — необязательный документ-описание таблиц (README, словарь
колонок, не больше 1 МБ в UTF-8): из него в паспорт попадают названия и
описания колонок (фоновая задача после ответа). Повторное подключение без
`description` названия из прошлого документа не стирает: сравнивается
только комментарий колонки.

Ответ `200`:

```json
{"datasource_id": "pg_1a2b3c4d5e", "kind": "postgres", "tables": ["orders", "users"], "profiles": [...]}
```

`datasource_id` стабилен для одного источника (хост, порт, база,
пользователь, схема) и не зависит от значения пароля.

| Код | Когда |
|---|---|
| 400 | некорректная строка подключения (`ValueError`) |
| 413 | `description` больше 1 МБ |
| 422 | неизвестный `kind` (валидация pydantic) |
| 422 | не удалось профилировать таблицу (`duckdb.Error`); подключение откатывается |
| 502 | PostgreSQL или ClickHouse недоступен или отклонил подключение |
| 503 | в DuckDB нет расширения `postgres_scanner` или `clickhouse_scanner` |

Тексты ошибок — на русском и никогда не содержат пароль.

Таблица, на которую у пользователя нет прав `SELECT`, не подключается:
профиль её не прочитал, представление удаляется, в лог пишется
`logging.warning`, остальные таблицы схемы подключаются. Любая другая
ошибка профиля откатывает подключение (`PostgresConnector.rollback` снимает
представления и `ATTACH`). Прежнее подключение того же источника к этому
моменту уже снято, источник нужно подключить заново.

`DELETE /api/datasources/{datasource_id}` отключает источник: снимает его
представления, отсоединяет базу, удаляет секрет, паспорта его таблиц и
сохранённую запись. Ответ `204`; `404`, если такого источника нет. После
этого источник не переподключается при старте.

### Строка подключения

Модуль `connectors/pg_dsn.py` принимает два формата:

- URI: `postgresql://user:password@host:port/dbname?sslmode=require`
  (схема `postgresql://` или `postgres://`, спецсимволы в пароле — в
  percent-кодировке, например `@` -> `%40`);
- libpq «ключ=значение»: `host=db.local port=5432 dbname=shop user=analyst password='p w'`.

Проверки до любого обращения к сети (иначе `ValueError`): строка не пуста,
формат распознан, у URI поддерживаемая схема и корректный порт, кавычки
закрыты, **указан хост** (`host` или `hostaddr`). Если не задан
`connect_timeout`, подставляется 10 секунд — недоступный сервер не
подвешивает запрос.

Для логов и сообщений используется маскированная форма
`postgresql://analyst:***@db.local:5432/shop` (`PostgresDsn.masked()`,
`repr`/`str` коннектора и DSN).

### Последовательность `PostgresConnector.connect(db)`

1. `INSTALL postgres_scanner` — без сети может не выполниться; это не
   ошибка, если расширение уже установлено в образ.
2. `LOAD postgres_scanner` — если не загрузилось, расширения нет:
   `PostgresExtensionUnavailableError`. В замкнутом контуре расширение
   должно быть заранее установлено в образ бэкенда (issue-06).
3. Если в DSN есть пароль — `CREATE OR REPLACE TEMPORARY SECRET <alias>_secret (TYPE postgres, PASSWORD $password)`;
   пароль передаётся параметром запроса и не попадает в текст SQL.
4. `ATTACH 'host=... port=... dbname=... user=...' AS <alias> (TYPE postgres, READ_ONLY[, SECRET <alias>_secret])`.
5. `SELECT table_name FROM <alias>.information_schema.tables WHERE table_schema = $schema ORDER BY table_name`
   — в список попадают и таблицы, и представления PostgreSQL.
6. Прежнее подключение того же источника (если было) снимается: его view
   удаляются, база отсоединяется, секрет удаляется.
7. Пустая схема -> `[]` и `logging.warning`. Больше `DB_MAX_TABLES`
   таблиц (по умолчанию 50, `.env`; прежнее имя `POSTGRES_MAX_TABLES` тоже читается) -> берутся первые по алфавиту,
   `logging.warning`.
8. На каждую таблицу — `CREATE OR REPLACE TEMP VIEW "<имя>" AS SELECT * FROM <alias>."<схема>"."<таблица>"`.
9. `logging.info`: источник (без пароля), число таблиц, время подключения.

После этого запрос `SELECT * FROM orders` работает так же, как для CSV.

### Решения и их причины

**Пароль — только в секрете DuckDB.** Строка из `ATTACH` видна любому SQL
через `duckdb_databases()` и повторяется в текстах ошибок libpq. Поэтому
`ATTACH` получает строку без пароля, а пароль лежит во временном секрете
(в `duckdb_secrets()` он показан как `redacted`). Секрет должен жить, пока
база подключена: расширение открывает новые соединения по мере надобности.
Секрету нужна именно строка «ключ=значение»: с URI DuckDB не может
объединить параметры секрета — поэтому URI всегда переводится в этот вид.

**Новый алиас на каждое подключение.** Алиас — `pg_<хеш источника>_<случайный
токен>`. Прежнее подключение того же источника снимается только после того,
как новое успешно открылось и вернуло список таблиц. Неудачная попытка
(например, с неверным паролем) не ломает рабочий источник.

**Временные представления (TEMP).** `ATTACH` не сохраняется в файле
`main.duckdb`, а обычный `VIEW` сохранился бы и после перезапуска ссылался
на исчезнувшую базу. TEMP-представления живут, пока открыто соединение,
поэтому после перезапуска бэкенд переподключает источник сам (см.
«Восстановление после перезапуска»).

Ограничение: временные объекты DuckDB видны **только в том соединении**, в
котором созданы. Сейчас `DuckDBManager` держит одно соединение на всё
приложение (`app.state.db`), и это работает. Если в будущем появятся
`cursor()`/отдельные соединения на сессию, подключать источник нужно в том
же соединении, где выполняются запросы.

**Конфликт имён.** Если имя таблицы уже занято другим объектом DuckDB
(например, CSV `events` или таблицей из другой базы), представление
получает имя `<dbname>_<таблица>`, затем `<алиас>_<таблица>`, затем
`<алиас>_<таблица>_<N>`. Сравнение без учёта регистра, как в DuckDB. О
переименовании пишется `logging.warning`; итоговые имена — в `tables`
ответа.

**Экранирование.** Имена схем и таблиц всегда в двойных кавычках (таблица
`"Mixed Case"` работает), имя схемы в запрос к `information_schema`
передаётся параметром.

**Потоки.** Обработчик `/api/datasources/db` синхронный — FastAPI выполняет
его в пуле потоков, подключение к PostgreSQL не блокирует цикл событий.
`DuckDBManager.query/execute` и вся последовательность `connect()`
выполняются под `DuckDBManager.lock`.

**Большие схемы.** Проверено на схеме из 1500 таблиц (локальный
PostgreSQL 17): подключение с лимитом 50 занимает около 0,4 с, повторное — около
0,1 с. Лимит отбирает первые таблицы в лексикографическом порядке
(`t1, t10, t100, ...`), а не «самые важные».

### Восстановление после перезапуска

Модуль `core/data/restore.py`, хранилище `core/memory/datasource_store.py`.

1. После успешного `POST /api/datasources/db` источник сохраняется в SQLite
   (`SQLITE_PATH`, таблица `datasources`): `identity`, `kind`, `dsn`,
   `db_schema`, `description`, `created_at`. Повторное подключение того же
   источника перезаписывает строку.
2. В `dsn` лежит только маскированная строка `PostgresDsn.masked()`
   (`postgresql://analyst:***@db.local:5432/shop`). Пароль на диск не
   попадает: при старте он берётся из переменной `POSTGRES_PASSWORD__<identity>`
   (например, `POSTGRES_PASSWORD__pg_1a2b3c4d5e`), иначе из общей
   `POSTGRES_PASSWORD`. Переменные окружения процесса важнее `.env`,
   `backend/.env` важнее корневого — как у остальных настроек. В Docker
   бэкенд получает их из `.env` через `env_file`. Источник без пароля в
   строке подключения (`trust`, `.pgpass` не используется) пароля не требует.
3. `lifespan` запускает `restore_saved_sources` фоновой задачей: старт не
   ждёт PostgreSQL. Источники переподключаются по очереди, каждый в
   отдельном потоке под `DuckDBManager.lock` и с таймаутом
   `POSTGRES_RESTORE_TIMEOUT_S` (60 с). Недоступный сервер, отсутствующее
   расширение, неверный пароль или истёкший таймаут пишутся в лог как
   `WARNING` и не мешают остальным источникам; нет пароля — `WARNING` с
   именем нужной переменной.
4. Переподключение — `ingest.restore`: тот же `connect()` (имена
   представлений совпадают с прежними, если их не занял новый объект —
   тогда работает обычное правило конфликта имён). Таблица с паспортом не
   профилируется заново, если колонки представления совпадают с колонками
   паспорта; изменилась схема в PostgreSQL или паспорта нет — профиль
   пересчитывается. Ошибки профиля обрабатываются как при подключении:
   таблица без прав `SELECT` пропускается (`skip` удаляет представление,
   её паспорт тоже удаляется), остальные таблицы восстанавливаются; любая
   другая ошибка откатывает подключение (`rollback`), источник пишется в лог
   как не восстановленный.
5. `DELETE /api/datasources/{id}` удаляет запись, поэтому отключённый
   источник больше не восстанавливается.

Ограничения: `masked()` хранит только пользователя, хост, порт и базу, поэтому
дополнительные параметры строки подключения (`sslmode`, `options`, …) после
перезапуска не восстанавливаются — действуют значения libpq по умолчанию.
Истёкший таймаут не прерывает поток с `ATTACH`: он доработает в фоне и
держит `DuckDBManager.lock`, пока libpq не вернёт управление
(`connect_timeout`, 10 с). Пока идёт восстановление, запросы к таблицам
источника отвечают «таблица не найдена».

`DuckDBManager.columns()` ищет и во временных представлениях (каталог
`temp`), иначе сессию над таблицей PostgreSQL нельзя было создать. Если имя
есть и в `temp`, и в основной базе, колонки берутся из `temp`, как и у
`SELECT * FROM <имя>`.

### Известные ограничения

- Расширение `postgres_scanner` устанавливается при сборке образа бэкенда
  (`backend/Dockerfile`), поэтому в контейнере коннектор работает без сети. При запуске
  без Docker и без сети расширение нужно установить заранее, иначе — 503.
- После перезапуска бэкенда источник с паролем восстанавливается, только
  если пароль задан в `POSTGRES_PASSWORD__<identity>` или `POSTGRES_PASSWORD`.
- У `DUCKDB_PATH` относительный путь по умолчанию (`backend/storage/...`): при запуске
  из `backend/` или в Docker (`WORKDIR /app`, том `/app/storage`) файл базы окажется
  не там, где ожидается. Теперь `DuckDBManager` открывается при старте приложения,
  поэтому путь стоит задавать явно через `.env`.

### Сообщения об ошибках

| Причина (по тексту ошибки libpq) | Сообщение |
|---|---|
| неверный пользователь/пароль | «PostgreSQL отклонил учётные данные…» |
| хост не найден | «Не удалось найти хост PostgreSQL…» |
| отказ в соединении, таймаут, нет сети | «Сервер PostgreSQL недоступен…» |

| прочее | «Не удалось подключиться к PostgreSQL.» |

К сообщению добавляется маскированный источник. Исходный текст ошибки
(без пароля) пишется в лог на уровне `WARNING`.

## ClickHouse
Пользователь передаёт строку подключения с нативным портом ClickHouse:

```text
clickhouse://[user[:password]@]host[:9000]/database
clickhouses://[user[:password]@]host[:9440]/database
```

`clickhouses://` используется для защищённого native TCP-подключения. Пароль
передаётся в DuckDB Secret и не включается в строку `ATTACH`, логи или сообщения
об ошибках.

Коннектор использует только community extension DuckDB `clickhouse_scanner`.

1. Загружает расширение (`LOAD clickhouse_scanner`; при необходимости сначала
   пытается выполнить `INSTALL clickhouse_scanner FROM community`).
2. Создаёт временный `SECRET` для пароля.
3. Подключает базу через `ATTACH ... (TYPE clickhouse, READ_ONLY, SECRET ...)`.
4. Получает список таблиц из каталога подключённой базы DuckDB с фильтром по
   `database=<alias>` и `schema=<database из DSN>`, поэтому таблицы других баз
   ClickHouse не импортируются.
5. Создаёт временные представления
   `SELECT * FROM <alias>.<database>.<table>`.

Данные читаются при выполнении запроса через удалённый scan, без загрузки
таблиц целиком в Python. Fallback через `clickhouse-connect` и отдельный
HTTP-клиент отсутствуют. Лимит строк коннектор не устанавливает: ограничение
результата задаётся самим SQL-запросом, а `DB_MAX_TABLES` ограничивает только
число подключаемых таблиц.

### Ограничения

- В окружении должен быть доступен совместимый с версией DuckDB community
  extension `clickhouse_scanner`.
- Для production/offline-образов расширение следует установить на этапе сборки;
  runtime `INSTALL` требует сетевого доступа и выполняется только как попытка
  восстановления.
- Discovery использует каталог DuckDB подключённой базы и фильтрует таблицы по
  выбранной схеме; `SHOW TABLES` без фильтра по базе не используется.
- `DB_MAX_TABLES` ограничивает количество создаваемых представлений, но не
  количество строк в удалённых таблицах.

### API

`POST /api/datasources/db`:

```json
{"kind": "clickhouse", "dsn": "clickhouse://localhost:9000/sber_demo"}
```

Ответ `200`:

```json
{
  "datasource_id": "ch_1a2b3c4d5e",
  "kind": "clickhouse",
  "tables": ["orders", "users"],
  "profiles": [...]
}
```

Коды ответа — как у PostgreSQL (таблица выше): 502 —
`ClickHouseConnectionError`, 503 — `ClickHouseExtensionUnavailableError`,
422 — сбой профиля, текст ошибки проходит через `ClickHouseConnector.scrub`.
Если таблиц больше `DB_MAX_TABLES`, подключаются первые по алфавиту, а
`ClickHouseConnector.warnings(table)` возвращает предупреждение об обрезке.

Причина в тексте 502 определяется по коду ClickHouse в тексте ошибки
(`Code: 81`, `ClickHouse error 516`; таблица `CLICKHOUSE_ERROR_CODES`), а без
кода — по маркерам (`describe_failure`): неизвестная база или таблица,
учётные данные, хост, сеть, права.

## Описания колонок из источника

`BaseConnector.column_comments(db, table) -> dict[str, str]` — комментарии
колонок `{колонка: описание}` — часть описания таблицы, которое энричер
переносит в паспорт как есть; `table` — имя, которое вернул
`connect()`. ClickHouse получает комментарии из `system.columns`.

- **PostgreSQL.** TEMP VIEW комментарии не переносит, поэтому они читаются из
  самого источника: `col_description()` по `pg_attribute`/`pg_class`/`pg_namespace`
  одним запросом `postgres_query(<alias>, ...)` в том же подключении. View
  сопоставляется с исходной таблицей через `connector.sources`
  (заполняется в `connect()`), поэтому работает и для view, переименованного
  из-за конфликта имён (`<dbname>_<таблица>`). Схема и таблица — литералы
  PostgreSQL внутри литерала DuckDB, кавычки экранируются дважды. Если запрос
  не удался, пишется предупреждение (без пароля), и возвращается `{}`.
- **CSV.** `duckdb_columns().comment` таблицы в схеме `main`. Загрузчик
  комментарии не задаёт (а `CREATE OR REPLACE TABLE` их сбрасывает), поэтому
  обычно там пусто: описание колонок CSV приходит документом-описанием.

## Профилирование при подключении

`core/data/profiling.py` строит «паспорт данных» таблицы:
`profile_table(db, table, *, approx=True, top_values_limit=20) -> TableProfile`.

### Контракт

- `TableProfile`: `table`, `row_count`, `column_count`, `columns`
  (список `ColumnStats`), `profiled_at` (UTC, ISO 8601). `to_dict()` даёт
  JSON-совместимый словарь (даты — строки ISO, `Decimal` — `float`),
  `column(name)` ищет колонку по имени.
- `ColumnStats` — по колонке: `name`, `dtype` (тип DuckDB как есть), `kind`
  (`numeric` / `identifier` / `temporal` / `text` / `bool` / `other`), `total`, `nulls`,
  `null_pct`, `nan_pct`, `distinct`, `distinct_pct`, `min`, `max`, `mean`,
  `median`, `std`, `q1`, `q3`, `iqr`, `p05`, `p95`, `skewness`, `kurtosis`,
  `mode`, `top_values` (`[{value, count}]`), `min_len`, `max_len`,
  `min_date`, `max_date`, `is_constant`, `is_unique`, `outlier_count`,
  `identifier_by` (`name` / `unique` / `fixed_width` / `None` — почему колонка стала `identifier`).

### Что считается для какого типа

| Тип (`kind`) | Метрики |
|---|---|
| все, кроме `other` | пропуски, `distinct`, топ-значений, мода, флаги |
| `numeric` | min/max, среднее, `stddev_pop`, квартили и p05/p95, IQR, скошенность, куртозис, выбросы; для `FLOAT`/`DOUBLE` ещё `nan_pct` |
| `identifier` (целое или число с именем-идентификатором либо значениями-кодами, см. ниже) | только общие метрики: `min`/`max`, среднее, квантили и выбросы — `None` |
| `temporal` (`DATE`, `TIMESTAMP*`) | `min_date`/`max_date` (они же `min`/`max`) |
| `text` (`VARCHAR`, `UUID`, `ENUM`) | min/max (лексикографически), `min_len`/`max_len` |
| `bool` | только общие метрики |
| `other` (`TIME`, `INTERVAL`, `BLOB`, списки, структуры) | только пропуски |

Тип колонки берётся из `DESCRIBE SELECT * FROM <таблица>` — тот же
результат, что `PRAGMA table_info`, но корректно работает с именами таблиц,
где есть кавычки и пробелы.

Правила, которые стоит знать:

- Числовая колонка (целые, `DECIMAL`, `FLOAT`/`DOUBLE`) получает
  `identifier` вместо `numeric`, если её имя похоже на идентификатор:
  имя без учёта регистра режется на слова по пробелам, `_` и знакам
  препинания, и среди слов есть `id` или `код` либо слово, начинающееся
  с `идентификатор`. Так попадают `ID_Аптеки`, `ID_Лекарства`, `user_id`,
  `id`, `Код аптеки`, `Идентификатор клиента`; остаются числовыми
  `Номер позиции`, `Номер события в сессии`, `Сколько_Купили`, `paid`.
  Основание — README датасетов хакатона: «Числовой код следует использовать
  как категорию, а не как показатель». Текстовые `Код …` остаются `text`.
  Слитное `pharmacyId` (camelCase) правило по имени не ловит — его ловит
  правило по значениям.
- Имена в чужих датасетах заранее неизвестны, поэтому целочисленная колонка
  становится `identifier` ещё и **по значениям** — после обоих проходов, без
  лишних запросов (нужные `min`, `max`, `distinct`, `is_unique` уже посчитаны):
  - `unique`: все значения различны, пропусков нет, строк не меньше 100,
    отрицательных нет (номер чека, ключ строки);
  - `fixed_width`: у `min` и `max` одинаковое число цифр (не меньше 4) — значит,
    у всех значений тоже, отрицательных нет, уникальных не меньше 10 и они
    плотно занимают диапазон (`distinct / (max − min + 1) ≥ 0,5`): коды
    `10001…10040`, `1001…1030`. Плотность отсекает показатели вроде цен
    `1000…9999`, у которых значения разбросаны по диапазону.

  Правило по значениям не применяется, если имя похоже на показатель
  (слово начинается с `сумм`, `цен`, `руб`, `колич`, `шт`, `год`, `врем`,
  `мс`, `показ`, `клик`, `оценк`, `amount`, `price`, `count`, `year`, … —
  полный список в `MEASURE_PREFIXES`): так `Год выпуска 2000…2024` остаётся
  числом. У колонки, ставшей `identifier` по значениям, числовые метрики и
  выбросы обнуляются, а в «Качество данных» попадает пояснение, чтобы LLM и
  пользователь видели, почему это категория. На 9 датасетах хакатона правило
  по значениям само находит `ID_Аптеки` и `ID_Лекарства` и не трогает ни одного
  из 17 остальных целочисленных показателей. Пределы правила: случайные
  целые «цены» из плотного диапазона без говорящего имени будут приняты за
  коды.

- Значения NaN в `FLOAT`/`DOUBLE` исключаются из всех числовых метрик,
  из `distinct` и топ-значений (иначе DuckDB считает NaN больше любого
  числа и портит max и квантили); их доля — в `nan_pct`.
- Доли в процентах: `null_pct` и `nan_pct` — от `total`,
  `distinct_pct` — тоже от `total`.
- `is_constant`: ровно одно уникальное непустое значение;
  `is_unique`: число уникальных равно числу строк (пропуск делает колонку
  неуникальной). Для таблицы из одной строки верны оба флага.
- `mode` — самое частое значение; если все значения встречаются по
  одному разу (и их больше одного), мода не определена и равна `None`.
  При равенстве частот топ-значений порядок — по строковому представлению.
- Выбросы — правило Тьюки: значения вне `[q1 − 1,5·IQR; q3 + 1,5·IQR]`.
- Квантили — `quantile_cont` (линейная интерполяция). Если `approx=True`
  и в таблице не меньше `PROFILE_APPROX_MIN_ROWS` строк (по умолчанию
  100 000), используется `approx_quantile` (t-digest). На малых таблицах
  он даёт заметно неверный результат (для `[1, 2, 2, 3, 100]` q3 = 27
  вместо 3), поэтому порог обязателен. `SchemaEnricher` берёт `approx` из
  настройки `PROFILE_APPROX_QUANTILE` (по умолчанию `true`).
- Скошенность и куртозис — выборочные (`skewness`, `kurtosis` DuckDB): им
  нужно минимум 3 и 4 значения, иначе `None`. Нечисловые результаты
  (NaN, бесконечность) превращаются в `None`.
- Пустая таблица: `row_count = 0`, все метрики `None`, флаги `False`.

### Сколько запросов

Не больше четырёх на таблицу при любом числе колонок:

1. `DESCRIBE` — схема.
2. `COUNT(*)` — только при `approx=True` и наличии числовых колонок,
   чтобы выбрать между точными и приближёнными квантилями.
3. Один `SELECT` со всеми агрегатами по всем колонкам (одно сканирование).
4. Один `SELECT` с частотами (для каждой колонки — подзапрос
   `GROUP BY` с `max_by(…, n)` для топ-значений и `COUNT(*)` групп для
   `distinct`) и подсчётом выбросов по границам из шага 3. Для пустой
   таблицы не выполняется.

Профилированию numpy/scipy не нужны — всё считает DuckDB (SciPy и NumPy
нужны только статистическим тулам `core/tools/stats/`).

### Производительность

`scripts/run_profile_benchmark.py` профилирует CSV из
`data/sample_datasets/` и синтетическую таблицу 1 000 000 строк × 50
колонок восьми типов. Лимит — 10 с на ноутбуке без GPU; его проверяют тест
`tests/benchmark/test_profile_benchmark.py` (маркер `benchmark`, в обычный


### Где используется паспорт

- `core/data/ingest.py` — `attach(connector, db)` вызывает профилирование
  сразу после `connector.connect()` для каждой таблицы и сохраняет профиль в
  паспорт (таблицы схемы `_meta`, `ProfileMemory`, см. [memory.md](memory.md)).
  Так подключают источник `POST /api/datasources/*`, `scripts/load_hk_datasets.py`
  и `scripts/run_full_llm_cycle.py`. Упало профилирование — подключённые
  таблицы откатываются (`connector.rollback`); таблицу, которую нельзя
  прочитать, коннектор может пропустить (`connector.skip`, у PostgreSQL —
  при `permission denied`).
- `core/data/schema_enrichment.py` — `SchemaEnricher` профиль не считает: если
  у таблицы есть описание, переносит из него в паспорт названия и описания
  колонок (см. [memory.md](memory.md#описание-таблицы--coredataschema_enrichmentpy)).
- `core/llm/prompts/schema_describe.py` — промпт «что передо мной»
  получает блок «Качество данных» (`format_quality`): пропуски, NaN,
  константы, выбросы, текстовые колонки, похожие на идентификаторы.
  Промпт `schema_describe` предупреждает модель, что колонки
  `identifier` — категории, а не показатели.
- `core/data/semantic_select.py` — `select_columns(question, columns,
  top_k, profile)`: основной вес — совпадение токенов вопроса с именем
  колонки; при переданном профиле вопросы об агрегатах (сумма, среднее,
  сколько…) поднимают числовые колонки (но не `identifier`), вопросы о
  динамике (тренд, по месяцам…) — колонки дат.
