# Реализовать планировщик шагов и ядро агентного цикла (orchestrator, SSE-чат, регистрация тулов) — блокирующий этап Фазы 1

## Что это и зачем

SberAnalyticalAgent — AI-Native BI-платформа: чат-агент-аналитик, который отвечает на вопросы о данных, строит графики и дашборды через диалог. Одна модель диалога — это **агентный цикл**, а не одна функция:

```text
вопрос пользователя
  ↓
1. Берём контекст: сессия, привязанные данные, словарь (если есть)
  ↓
2. Планировщик (LLM + Instructor) — делает план шагов: что вычислить, по каким колонкам, какие тулы
  ↓
3. Исполнитель шагов — запускает тул (SQL/агрегация/временные ряды/корреляция), при отсутствии тула и включённой генерации кода — генерирует код в песочницу
  ↓
4. Генерация финального вывода (инсайт) на бизнес-языке
  ↓
5. Визуализация: выбор графика → спека → данные → плитка/картинка
  ↓
6. Дашборд (если запрошен): сохраняем SQL + спеки в реестр
  ↓
7. Экспорт (опционально: xlsx/pdf)
  ↓
8. Обновляем память: история диалога, шаги, результаты
```

**Планировщик шагов** (`StepPlanner`) — это компилятор запроса в план действий: он получает вопрос, контекст сессии и список доступных тулов, и выдаёт структурированный `ResearchPlan` — упорядоченный набор `ResearchStep`, каждый из которых говорит исполнителю: «запусти тул X на колонках Y, если подходящего тула нет — генерируй код». Без рабочего планировщика и рабочего цикла, который его вызывает, агент не отвечает на вопросы, не рисует графики и не строит дашборды — это официальный блокирующий шаг Фазы 1 перед инструментами, словарём и интерактивом.

## Техническая реализация

1. **Модели-контракты.** В `backend/app/models/research_step.py` (и `backend/app/models/insight.py`, если ещё не создавали) создать Pydantic-схемы:
   - `ResearchStep`: `step_id`, `tool: str | None`, `columns: list[str]`, `needs_llm_codegen: bool`, `purpose: str`.
   - `ResearchPlan`: `steps: list[ResearchStep]`, `final_viz: str`, `dashboard_requested: bool`.
   - `Insight`: `headline: str`, `details: list[str]`, `limits: str`.

   Без этого оркестратор, исполнитель и парсер не запустятся: в коде уже есть импорты `from app.models.research_step import ...` и `from app.models.insight import ...`, но пакет `app/models` отсутствует.

2. **Регистрация тулов.** `ToolRegistry` настроен, но ни один тул не зарегистрирован: в `backend/app/core/tools/__init__.py` импортируются конкретные тулы (`AggregateTool`, `TimeSeriesTool`, `CorrelationTool`, `ForecastTool`, `SeasonalityTool`) и регистрируются в `tool_registry` (или добавить декоратор `@tool_registry.register` в `BaseTool`). Иначе `tool_registry.describe()` для LLM возвращает пустую строку, и планировщик не сможет выбирать инструменты.

3. **Ядро агентного цикла — `AgentOrchestrator`.** Конвейер уже задуман в `backend/app/core/agent/orchestrator.py` (вопрос → план → шаги → данные → инсайт → график → дашборд), но:
   - `build_context` нужно доделать: передавать в планировщик не пустой контекст — историю после подключения данных, отобранные колонки, словарь/описания.
   - Цепочка `result_table` должна течь от шага к шагу и сохраняться в память сессии. Обработка ошибок и ретраев пока не интегрирована: на ошибке цикл делает `yield error` и `return`, без возможности явного уточнения пользователя.
   - После цикла должна генерироваться итоговая таблица для инсайта, графика и (опционально) дашборда.

4. **Чат-стрим.** `POST /api/chat` заглушка ("TODO: orchestrator"). Нужно:
   - поднять `AgentOrchestrator()` и вызвать `await orchestrator.run(payload)`;
   - превратить генератор событий в `StreamingResponse(..., media_type="text/event-stream")`, где каждый элемент — `ChatEvent` (`text | chart | dashboard | error | done`);
   - оставить асинхронную обёртку, чтобы не блокировать event loop.
   Фронт (`frontend/src/api/client.ts`, `components/chat/ChatPanel.tsx`, `types/chat.ts`) уже готов к этим событиям — бэк реализует контракт.

5. **Обработка ошибок и восстановление.** Сделано в #39: упавший шаг исправляет планировщик по тексту ошибки (`StepPlanner.fix_step`, `agent/recovery.py`), `with_retry` удалён. Исходные требования:
   - при сбое тула — попробовать два раза, затем спросить пользователя, что делать (переформулировка / уточнение), и выдать чёткое сообщение;
   - при отсутствии тула и `needs_llm_codegen=true` — запустить `codegen_runner.run_generated_code` в WASM-песочнице, а не падать;
   - при невалидном JSON от LLM — `parser.py` переживает любой вывод и переходит на fallback-шаг с кодогенерацией.

6. **Тестовый фейковый LLM.** Для зачёта Фазы 1 без реальной модели добавить `FakeLLM` (заглушка `LLMClient`): фиксированный `ResearchPlan` на любой вопрос, персистентные данные из DuckDB (raw/demo_events), инлайн-инсайт и визуал. Это позволяет протестировать полный цикл вопрос → ответ → график → дашборд на CI без запуска локальной модели.

## Критерии приёмки

- `POST /api/chat` возвращает SSE-стрим событий `text → chart → done` для простого вопроса, показывая выполненный план шагов, сгенерированный инсайт и график (Vega-Lite-спека).
- Планировщик выдаёт непустой `ResearchPlan` (список шагов, финальная таблица = `raw`); при отсутствии подходящего тула — `needs_llm_codegen=true` и запуск в песочнице.
- Реестр тулов: модель видит `aggregate, time_series, correlation` и пр.; отсутствующий тул → fallback на генерацию кода.
- Состояние шагов сохраняется в DuckDB как `temp_result_vN` и используется при смене вида графика (`chart_morph`) без повторных вычислений.
- Интеграционный тест `tests/integration/test_agent_e2e.py` и E2E-scenario `tests/e2e/test_scenarios.py` пропускаются от локального Qwen только в случае отсутствия модели — иначе проходят.
- Модульные тесты для валидации `ResearchPlan`/`ResearchStep` и парсера шагов (`tests/unit/test_parser.py`) проходят.
