# SberAnalyticalAgent

**AI-Native BI-платформа**: диалоговый агент на базе LLM. Продуктовый аналитик
или руководитель на естественном языке исследует данные, получает графики и
собирает дашборды — без участия разработчика.

Внутри: DuckDB как единый SQL-движок над CSV, PostgreSQL и ClickHouse,
агент-планировщик с реестром аналитических инструментов, WASM-песочница
(Pyodide) для кода, который пишет LLM, Vega-Lite для графиков. LLM — любая
модель с OpenAI-совместимым API; рекомендуемая — **Qwen3.8-27B**.

- Архитектура — [Architecture.md](Architecture.md)
- Сценарии и критерии жюри с нашими результатами — [Criteria.md](Criteria.md)
- Прогоны вопросов организаторов — [TestCases.md](TestCases.md)

## Возможности

Мы делали платформу так, чтобы путь от вопроса до документа, который можно
отправить руководителю или соседнему отделу, шёл без швов: задал вопрос —
получил ответ с графиком — собрал дашборд — выгрузил отчёт или передал
коллеге всю сессию целиком.

### Ответ виден по мере работы

- Простые вопросы («Что передо мной?», «Что означает поле…») — за 10–20 секунд;
  «покажи то же самое в другом виде» — за 2–3 секунды, без нового обращения к модели.
- Модель рассуждает перед планом и перед выводом, а в чате видно, что
  происходит: шаги расчёта по мере выполнения, сколько уже написала модель.
  Ответ печатается по мере генерации.
- Ответ устроен одинаково: в заголовке — прямой ответ с числами, ниже — как
  посчитано и какие есть ограничения. На «как ты посчитал?» или «ты учитывал
  возвраты?» агент отвечает по журналу хода, ничего не пересчитывая.

### Режимы

Кнопки под полем ввода:

- **Дашборд** — агент предлагает четыре варианта дашборда по таблице (или
  ваш вариант) и собирает плитки: KPI, динамику, разрезы, с выводом к плиткам.
- **Проверка** — второй взгляд на ответ до того, как его увидит пользователь.
  Критик проверяет шаги и вывод, ловит методические ошибки (не тот
  знаменатель, забытые возвраты, не тот период) и сам исправляет ответ. На
  нашем наборе из 35 вопросов режим дал +40 % верных ответов: 14 против 10.
- **Глубокое исследование** — сначала агент уточняет задачу: цель, метрику,
  период, разрез, фильтр. Варианты можно выбрать кнопками или вписать свой.
  Потом агент исследует уже то, что нужно.

### Табло инсайтов

Все выводы сессии собираются на отдельном табло «Инсайты» в панели справа.
Каждая карточка — вопрос, вывод и график. По табло работает поиск, карточки
листаются стрелками, из любой можно вернуться к ходу в чате или скопировать
текст. Табло выгружается целиком или по результатам поиска — в PDF и в
Markdown: выводы удобно сразу отправить дальше.

### Дашборды

Дашборд собирается на канвасе: плитки перетаскиваются и меняют размер, у
каждой можно сменить тип графика, переименовать её или убрать. Любой график
из чата добавляется в один или несколько дашбордов. Плитки хранят снимок
данных, «Обновить данные» пересчитывает их. Все дашборды лежат в реестре
«Все дашборды», открываются по прямой ссылке и из сессии, где родились.

### Экспорт

Инсайтами делятся, поэтому экспорт сделан под тех, кто будет читать и
работать с результатом дальше.

- **PDF — деловой отчёт.** Вопрос, ключевой вывод, детали, график и таблица
  с подтверждающими данными. Оформление — в фирменной палитре Сбера, с
  кириллицей без артефактов и нумерацией «Страница X из Y». Дашборд
  выгружается одним отчётом: шапка с датой среза и источником, сетка KPI,
  карточки всех плиток с графиками и выводами.
- **Excel — для аналитиков и смежных отделов**, которые продолжат считать сами.
  Карточка с вопросом и выводом, таблица с автофильтром и закреплённой шапкой,
  нативная диаграмма Excel. Дашборд выгружается в книгу: лист «Сводка» с KPI и
  оглавлением-ссылками и по листу на каждую плитку с кнопкой «← Вернуться в
  Сводку». Ячейки защищены от формул-инъекций.
- Результат любого шага расчёта — «Скачать .xlsx».
- Табло инсайтов — PDF и Markdown.

### Сессию можно передать

«Поделиться сессией» — три способа на выбор:

- **ссылка** — ответы и графики, помещается в сообщение Telegram;
- **файл `.session`** — со всеми таблицами; получатель перетаскивает его в окно
  и видит то же, что автор;
- **рецепт без данных** — получатель подключает свою базу, нажимает
  «Пересчитать», и графики пересчитываются на его данных.

Пароль к базе никуда не попадает.

Диалог помнит контекст: «а теперь в другом виде», «подробнее про второй
пункт», вопрос «в ответ» на любое сообщение («Спросить об этом»).

### Начать просто

На стартовом экране — туториал из пяти шагов, от загрузки данных до
дашборда. После загрузки таблица описана простым языком, а агент подсказывает
вопросы, с которых можно начать.

## Запуск в Docker Compose

**1. Клонировать репозиторий**

```bash
git clone https://github.com/Terrum19/sber-analysis-agent.git   # или git@github.com:Terrum19/sber-analysis-agent.git
cd sber-analysis-agent
```

**2. Создать `.env` в корне репозитория** — пять строк:

```bash
cat > .env <<'EOF'
COMPOSE_LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_MODEL=qwen/qwen3.8-27b
LLM_API_KEY=<ваш ключ>
LLM_PREPARE_MODEL=false
EMBED_MODEL=
EOF
```

На Windows создайте файл `.env` в Блокноте с теми же пятью строками.

- `COMPOSE_LLM_BASE_URL` — адрес OpenAI-совместимого API модели, как его видит
  контейнер backend.
- `LLM_PREPARE_MODEL=false` — не готовить модель через Ollama: её здесь нет.
- `EMBED_MODEL=` — без модели эмбеддингов. Смена таблицы посреди диалога тогда
  работает по словам вопроса, остальное не меняется.

Остальные настройки имеют значения по умолчанию (`docker-compose.yml`,
`backend/app/config.py`); все переменные с пояснениями — в `.env.example`.

**3. Собрать и запустить**

```bash
docker compose up -d --build
```

Первая сборка — 5–10 минут: скачиваются базовые образы и зависимости,
песочница Pyodide и расширения DuckDB для PostgreSQL и ClickHouse.

**4. Проверить, что всё поднялось**

```bash
docker compose ps                              # backend и frontend: (healthy)
curl -s http://localhost:8000/health           # {"status":"ok"}
curl -s http://localhost:8000/api/llm/status   # "state":"ok" — модель отвечает
```

Откройте http://localhost:3000.

**5. Загрузить данные и спросить**

1. Слева «Загрузка CSV» → выберите CSV (например, файл из
   [HK_Datasets](https://gitverse.ru/kban/HK_Datasets)). По желанию приложите
   README датасета как описание: из него в паспорт таблицы попадут названия и
   смысл колонок.
2. После загрузки откроется новая сессия над этой таблицей — задайте вопрос,
   например «Что передо мной?». Ещё одна сессия по той же базе — «+» у её
   названия слева.

Вместо CSV можно подключить базу: «Подключение базы данных» → PostgreSQL или
ClickHouse, строка подключения вида `postgresql://user:pass@host:5432/db` или
`clickhouse://user:pass@host:9000/db`. База на той же машине доступна из
контейнера как `host.docker.internal`.

**Остановить:** `docker compose down`. Данные, сессии и дашборды лежат в
`backend/storage/` и переживают перезапуск.

### Модель

Платформа работает с любым OpenAI-совместимым сервером. Выбор задают три
переменные в `.env`: `COMPOSE_LLM_BASE_URL` (адрес для backend в контейнере),
`LLM_MODEL` и, если нужен, `LLM_API_KEY`.

**Ollama на этой машине.** Нужны видеокарта от 24 ГБ или Mac с Apple Silicon
от 32 ГБ памяти. Установите [Ollama](https://ollama.com) и запустите её так,
чтобы контейнеры её видели. На Linux:
`OLLAMA_HOST=0.0.0.0 ollama serve`; на Mac и Windows — достаточно запущенного
приложения. В `.env`:

```bash
LLM_MODEL=qwen3.8:27b
```

`COMPOSE_LLM_BASE_URL` не задавайте: по умолчанию backend идёт в Ollama на
хосте (`http://host.docker.internal:11434/v1`). При старте backend сам скачает
модель (17,7 ГБ, прогресс — над чатом и в `GET /api/llm/status`) и создаст её
вариант с контекстом 16 384 токена: у Ollama по умолчанию 4096, длинный промпт
обрезался бы молча. Эмбеддинги (`bge-m3`) он скачает с той же Ollama.

**Ollama в контейнере на GPU NVIDIA** (нужен NVIDIA Container Toolkit):

```bash
LLM_MODEL_GPU=qwen3.8:27b make up-gpu
```

**vLLM на GPU-сервере:**

```bash
MODEL=Qwen/Qwen3.8-27B bash infra/vllm/serve.sh   # OpenAI API на :8001
```

В `.env` платформы: `COMPOSE_LLM_BASE_URL=http://<адрес сервера>:8001/v1`,
`LLM_MODEL=Qwen/Qwen3.8-27B`, `LLM_PREPARE_MODEL=false`, `EMBED_MODEL=`.

Другие модели подключаются так же, сменой `LLM_MODEL`. Сравнение моделей,
на которых мы тестировали агента, — в [Criteria.md](Criteria.md#модели).

## Другие способы запуска

### Без Docker: backend и frontend на машине

Нужны Python 3.11+, Node.js 20+ и npm.

```bash
# 1) Зависимости backend (в виртуальном окружении .venv в корне репозитория)
python3 -m venv .venv
source .venv/bin/activate              # Windows: .venv\Scripts\activate
pip install -r backend/requirements.txt

# 2) Песочница для кода от LLM (Pyodide) и расширения DuckDB для PostgreSQL/ClickHouse
(cd backend/sandbox && npm ci && python fetch_packages.py)
python -c "import duckdb; c = duckdb.connect(); c.execute('INSTALL postgres_scanner'); c.execute('INSTALL clickhouse_scanner FROM community')"

# 3) Зависимости frontend
(cd frontend && npm ci)

# 4) .env в корне — как для Docker, но адрес модели в LLM_BASE_URL
cat > .env <<'EOF'
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_MODEL=qwen/qwen3.8-27b
LLM_API_KEY=<ваш ключ>
LLM_PREPARE_MODEL=false
EMBED_MODEL=
EOF

# 5) Запуск: backend на :8000, frontend на :3000; остановить — Ctrl+C
make dev                               # то же самое: bash infra/local-dev.sh
```

С Ollama на этой же машине в `.env`: `LLM_BASE_URL=http://localhost:11434/v1`,
`LLM_MODEL=qwen3.8:27b`, строки `LLM_PREPARE_MODEL` и `EMBED_MODEL` уберите.

### Скрипты одного клика (Ollama на машине)

`start.command` (Mac), `start.bat` (Windows), `./start.sh` (Linux) запускают
Docker, ставят и запускают Ollama вне контейнера, поднимают платформу и
открывают http://localhost:3000. Остановить — `stop.command` / `stop.bat` /
`./stop.sh`. Модель — `LLM_MODEL` из `.env`, без него —
`qwen2.5-coder:7b`; для рекомендуемой модели добавьте в `.env`
`LLM_MODEL=qwen3.8:27b`.

### Make-цели

```bash
make up          # docker compose, Ollama на хосте
make up-ollama   # + Ollama в контейнере на CPU (профиль ollama)
make up-gpu      # + Ollama в контейнере на GPU NVIDIA (профиль ollama-gpu), модель LLM_MODEL_GPU
make down        # остановить всё, включая Ollama в контейнере и демо-БД
```

Демо-PostgreSQL и ClickHouse (пользователь и пароль `sber`, база `sber_demo`):
`docker compose --profile integration up -d postgres clickhouse`. Backend в той
же сети compose видит их как `postgres:5432` и `clickhouse:9000`.

## Для разработчиков

Модель для платформы готовит backend (`core/llm/ollama_setup.py`): при старте
скачивает `LLM_MODEL`, если её нет на сервере Ollama, и работает с её вариантом
с контекстом `LLM_NUM_CTX` (`<модель>-ctx<число>`); состояние — `GET /api/llm/status`.
Отключить — `LLM_PREPARE_MODEL=false`. Переменные окружения перекрывают `.env`:
`LLM_MODEL_GPU=qwen3.8:27b make up-gpu`.

Свой сервер LLM для compose — `COMPOSE_LLM_BASE_URL`; `LLM_BASE_URL` — только
для запуска без Docker: в контейнере `localhost` — сам backend. Ollama в
контейнере доступна с этой машины на `http://localhost:${OLLAMA_PORT:-11435}`.

Демо-данные для разработки: `python scripts/seed_demo_data.py`; датасеты
хакатона в DuckDB: `make hk-data`.

### Eval агента

`scripts/eval.py` прогоняет набор `data/eval/questions.yaml` через оркестратор и
пишет отчёт `docs/reports/eval_<дата>_<модель>.md` с JSON рядом: pass % всего и по
сценариям, p50/p95 времени ответа, recall отбора колонок, провалы с причинами.
Датасеты — `make hk-data`, backend на время прогона остановите.

```bash
make eval MODEL=qwen2.5-coder:7b   # настоящая модель (LLM_BASE_URL)
make eval EVAL_ARGS=--fake         # FakeLLM, без модели
```

Параметры, проверки и формат отчёта — `docs/eval.md`.

### Переход к другим данным посреди сессии

Перед каждым вопросом агент проверяет, не про другие ли он данные
(`relations.switch_table`). Сначала по словам: другая таблица названа по имени
или названию, а с текущей не совпало ни одно слово. Затем по смыслу —
эмбеддинги `EMBED_MODEL` (по умолчанию `bge-m3`): «а погода?» находит таблицу
«Температура по дням», хотя слов общих нет. Переход — только если другая
таблица ближе текущей на `MEANING_MARGIN`. Продолжения («а в процентах?»)
остаются на текущей. Модель эмбеддингов Ollama скачивает сама (backend — на
Ollama вне контейнера, entrypoint — в контейнере). Другой сервер —
`EMBED_BASE_URL`, пусто `EMBED_MODEL` — переход только по словам.

### Длина контекста LLM

Промпт планировщика — около 12 тыс. символов, это 4–5 тыс. токенов. У Ollama
контекст по умолчанию 4096 токенов, и не влезшее начало промпта отбрасывается
без ошибки: модель не видит список инструментов. С Ollama backend решает это сам:
работает с вариантом модели с `num_ctx = LLM_NUM_CTX` (по умолчанию 16384), который
создаёт при старте. Вручную контекст нужен, только если `LLM_PREPARE_MODEL=false`
или сервер не Ollama:

- Ollama, запущенная руками: `OLLAMA_CONTEXT_LENGTH=16384 ollama serve`.
- Ollama как служба systemd: `sudo systemctl edit ollama`, в `[Service]` —
  `Environment="OLLAMA_CONTEXT_LENGTH=16384"`, затем `sudo systemctl restart ollama`.
- Или модель с контекстом в Modelfile: `FROM qwen2.5-coder:14b` и
  `PARAMETER num_ctx 16384`, `ollama create qwen2.5-coder-16k -f Modelfile`,
  `LLM_MODEL=qwen2.5-coder-16k`.
- vLLM: `infra/vllm/serve.sh` передаёт `--max-model-len` (`MAX_MODEL_LEN`, по
  умолчанию `LLM_NUM_CTX`).

`options.num_ctx` в запросе к OpenAI-совместимому `/v1` Ollama игнорирует. Проверка:
`python3 scripts/check_llm_client.py` отправляет промпт 12 тыс. символов с паролем
в начале и печатает `prompt_tokens` и виден ли пароль. Бэкенд при первом ответе
спрашивает контекст у сервера и пишет warning, если он меньше `LLM_NUM_CTX`, а
каждый обрезанный промпт — warning «Промпт обрезан сервером LLM».

### Логи

Бэкенд пишет лог в консоль (`docker compose logs backend`, при `make dev` — в
терминал) и в файл `backend/storage/logs/backend.log` (в контейнере
`/app/storage/logs/backend.log`). Файл лежит на томе `./backend/storage` и
переживает `docker compose down`; при 5 МБ он ротируется, хранятся три прошлых
файла (`backend.log.1` … `backend.log.3`).

Формат строки: `время уровень [сессия/ход] модуль: сообщение`. Строки одного хода
помечены его `session_id` и `turn_id` — и строки планировщика, тулов, LLM и
песочницы. Вне хода вместо них `-`. На INFO ход виден целиком:

```text
… INFO [f0eb…/9940…] app.core.agent.orchestrator: ход начат: вопрос='Сумма по категориям'
… INFO [f0eb…/9940…] app.core.agent.orchestrator: маршрут: план
… INFO [f0eb…/9940…] app.core.agent.orchestrator: план за 3.2 с: шагов=1 [0 aggregate] final_viz=bar dashboard=False
… INFO [f0eb…/9940…] app.core.agent.orchestrator: шаг 0 готов за 7 мс: temp_result_v1
… INFO [f0eb…/9940…] app.core.agent.turn_log: инсайт за 4.1 с
… INFO [f0eb…/9940…] app.core.agent.turn_log: график bar за 0.1 с
… INFO [f0eb…/9940…] app.core.agent.turn_log: итог хода: ok за 7.5 с
```

- Маршрут: `small talk`, `обзор таблицы`, `смена вида графика`, `план` или
  `ответ на уточнение`.
- Итог хода — одна строка: `ok`, `failed`, `clarification` или `disconnected`
  (клиент закрыл поток), общее время, а для неуспешного хода — этап (`start`,
  `planning`, `step N`, `insight`, `chart`) и причина. `failed` и `disconnected` —
  на уровне WARNING.
- Вызов LLM: модель, схема ответа, время, `prompt_tokens` и длина ответа. Сбой —
  тип (таймаут, соединение, `HTTP <код>`), адрес сервера без логина и пароля и
  сколько ждали.
- При старте — одна строка `старт:` с моделью, адресом LLM, structured mode,
  контекстом, таймаутом и путём к файлу логов; ключи и DSN не пишутся.

Уровень задаёт `LOG_LEVEL` (`DEBUG`, `INFO` — по умолчанию, `WARNING`, `ERROR`).
На `DEBUG` в лог идут промпты и ответы модели целиком; на `INFO` их нет. httpx,
openai и instructor всегда на WARNING. В логе есть вопросы пользователей, поэтому
он хранится только локально в `storage/`.

Найти ход: `turn_id` приходит фронту в событии `done` (и `clarification_needed`).

```bash
docker compose logs backend | grep <turn_id>
grep <turn_id> backend/storage/logs/backend.log*
grep 'итог хода: failed' backend/storage/logs/backend.log   # все упавшие ходы
```
