# SberAnalyticalAgent

**AI-Native BI-платформа**: аналитик или руководитель задаёт вопрос о данных
обычным языком и получает ответ, график или дашборд — без SQL и без
разработчика. Агент на локальной LLM (Qwen 2.5-Coder через Ollama) планирует
исследование по шагам, считает в DuckDB и пишет Python в WASM-песочнице.
Всё работает в **замкнутом контуре**: данные и модель не покидают машину.

## Закрываемые сценарии

1. Первичное знакомство с неизвестными данными («Что передо мной?»)
2. Ответы на вопросы по содержанию («Какие значения встречаются чаще?»)

6. Диалог с контекстом («А теперь то же самое в другом виде»)

## Запуск

Нужна одна программа — [Docker Desktop](https://www.docker.com/products/docker-desktop/)
(на Linux подойдёт и Docker Engine с Compose 2.24+). Всё остальное делает скрипт запуска:

| Система | Что сделать |
|---|---|
| Mac | двойной клик по `start.command` |
| Windows | двойной клик по `start.bat` |
| Linux | `./start.sh` |

Скрипт сам запускает Docker, если тот не запущен, ставит и запускает
[Ollama](https://ollama.com) (вне контейнера: на Mac она работает на Metal, на
Windows — на видеокарте), поднимает платформу и открывает http://localhost:3000.
Повторный запуск пропускает то, что уже установлено и работает. Остановить —
`stop.command` / `stop.bat` / `./stop.sh` (данные и модель сохраняются). Ollama,
которую запустил скрипт, тоже останавливается; запущенную до него — нет.

Первый запуск — 10–20 минут и нужен интернет: собираются образы, а модель
(`qwen2.5-coder:7b`, около 5 ГБ) скачивает сама платформа. Пока модель
скачивается, над чатом виден прогресс; данные загружать уже можно. Памяти
рекомендуется от 16 ГБ: модели 7B самой нужно около 6 ГБ.

На Mac при первом открытии `start.command` система может спросить, доверяете
ли вы файлу: правый клик → «Открыть». На Linux скрипт берёт Ollama на этой
машине, а если её нет — ставит официальным установщиком (спросит пароль sudo)
и запускает на адресе моста docker: контейнерам её видно, локальной сети — нет.
Уже запущенную службу берёт, если она видна из контейнеров, и сам её не
перенастраивает. Если хостовую Ollama контейнерам не видно — Ollama в контейнере
(с NVIDIA Container Toolkit — на GPU и с моделью `LLM_MODEL_GPU`), и скрипт
говорит об этом.
Службы запускаются и без systemd (`service`).

## Для разработчиков

Модель для платформы готовит backend (`core/llm/ollama_setup.py`): при старте
скачивает `LLM_MODEL`, если её нет на сервере Ollama, и работает с её вариантом
с контекстом `LLM_NUM_CTX` (`<модель>-ctx<число>`); состояние — `GET /api/llm/status`.
Отключить — `LLM_PREPARE_MODEL=false`. `.env` не обязателен: значения по
умолчанию — в `docker-compose.yml` и `backend/app/config.py`, пример — `.env.example`.

```bash
make up          # docker compose, Ollama на хосте (http://host.docker.internal:11434)
make up-ollama   # Ollama в контейнере на CPU (профиль ollama)
make up-gpu      # Ollama в контейнере на GPU NVIDIA (профиль ollama-gpu), модель LLM_MODEL_GPU
make down
```

Свой сервер LLM (vLLM, GPU-машина в сети) для compose: `COMPOSE_LLM_BASE_URL` в
`.env`, например `http://10.0.0.5:8001/v1` (`LLM_BASE_URL` — только для `make dev`:
в контейнере `localhost` — сам backend). Ollama в контейнере доступна с этой
машины на `http://localhost:${OLLAMA_PORT:-11435}`. Демо-PostgreSQL и ClickHouse
для интеграционных тестов — профиль `integration`.

Нужны Docker Engine 25+ и Docker Compose 2.24+ (`start_interval` в healthcheck,
`depends_on.required`, необязательный `env_file`): `docker compose version`.

Без Docker:

```bash
# 1) LLM (замкнутый контур): Ollama или vLLM; контекст backend задаст сам (ниже)
ollama serve
# или GPU: MODEL=Qwen/Qwen2.5-Coder-14B-Instruct bash infra/vllm/serve.sh

- **GPU NVIDIA:** `make up-gpu` вместо `make up` (нужен NVIDIA Container Toolkit);

- **Остановить:** `make down`. Данные (подключённые таблицы, сессии, дашборды)

- **Порты:** интерфейс 3000, API 8000 (документация API — http://localhost:8000/docs),

### Eval агента

`scripts/eval.py` прогоняет набор `data/eval/questions.yaml` через оркестратор и
пишет отчёт `docs/reports/eval_<дата>_<модель>.md` с JSON рядом: pass % всего и по
сценариям, p50/p95 времени ответа, recall отбора колонок, провалы с причинами.
Датасеты — `make hk-data`, backend на время прогона остановите.

```bash
make eval MODEL=qwen2.5-coder:7b   # настоящая модель (LLM_BASE_URL)
make eval EVAL_ARGS=--fake         # FakeLLM, без модели
```

Параметры, проверки и формат отчёта — `docs/eval.md`.

### Переход к другим данным посреди сессии

Перед каждым вопросом агент проверяет, не про другие ли он данные
(`relations.switch_table`). Сначала по словам: другая таблица названа по имени
или названию, а с текущей не совпало ни одно слово. Затем по смыслу —
эмбеддинги `EMBED_MODEL` (по умолчанию `bge-m3`): «а погода?» находит таблицу
«Температура по дням», хотя слов общих нет. Переход — только если другая
таблица ближе текущей на `MEANING_MARGIN`. Продолжения («а в процентах?»)
остаются на текущей. Модель эмбеддингов Ollama скачивает сама (backend — на
Ollama вне контейнера, entrypoint — в контейнере). Другой сервер —
`EMBED_BASE_URL`, пусто `EMBED_MODEL` — переход только по словам.

### Длина контекста LLM

Промпт планировщика — около 12 тыс. символов, это 4–5 тыс. токенов. У Ollama
контекст по умолчанию 4096 токенов, и не влезшее начало промпта отбрасывается
без ошибки: модель не видит список инструментов. С Ollama backend решает это сам:
работает с вариантом модели с `num_ctx = LLM_NUM_CTX` (по умолчанию 16384), который
создаёт при старте. Вручную контекст нужен, только если `LLM_PREPARE_MODEL=false`
или сервер не Ollama:

- Ollama, запущенная руками: `OLLAMA_CONTEXT_LENGTH=16384 ollama serve`.
- Ollama как служба systemd: `sudo systemctl edit ollama`, в `[Service]` —
  `Environment="OLLAMA_CONTEXT_LENGTH=16384"`, затем `sudo systemctl restart ollama`.
- Или модель с контекстом в Modelfile: `FROM qwen2.5-coder:14b` и
  `PARAMETER num_ctx 16384`, `ollama create qwen2.5-coder-16k -f Modelfile`,
  `LLM_MODEL=qwen2.5-coder-16k`.
- vLLM: `infra/vllm/serve.sh` передаёт `--max-model-len` (`MAX_MODEL_LEN`, по
  умолчанию `LLM_NUM_CTX`).

`options.num_ctx` в запросе к OpenAI-совместимому `/v1` Ollama игнорирует. Проверка:
`python3 scripts/check_llm_client.py` отправляет промпт 12 тыс. символов с паролем
в начале и печатает `prompt_tokens` и виден ли пароль. Бэкенд при первом ответе
спрашивает контекст у сервера и пишет warning, если он меньше `LLM_NUM_CTX`, а
каждый обрезанный промпт — warning «Промпт обрезан сервером LLM».

### Логи

Бэкенд пишет лог в консоль (`docker compose logs backend`, при `make dev` — в
терминал) и в файл `backend/storage/logs/backend.log` (в контейнере
`/app/storage/logs/backend.log`). Файл лежит на томе `./backend/storage` и
переживает `docker compose down`; при 5 МБ он ротируется, хранятся три прошлых
файла (`backend.log.1` … `backend.log.3`).

Формат строки: `время уровень [сессия/ход] модуль: сообщение`. Строки одного хода
помечены его `session_id` и `turn_id` — и строки планировщика, тулов, LLM и
песочницы. Вне хода вместо них `-`. На INFO ход виден целиком:

```text
… INFO [f0eb…/9940…] app.core.agent.orchestrator: ход начат: вопрос='Сумма по категориям'
… INFO [f0eb…/9940…] app.core.agent.orchestrator: маршрут: план
… INFO [f0eb…/9940…] app.core.agent.orchestrator: план за 3.2 с: шагов=1 [0 aggregate] final_viz=bar dashboard=False
… INFO [f0eb…/9940…] app.core.agent.orchestrator: шаг 0 готов за 7 мс: temp_result_v1
… INFO [f0eb…/9940…] app.core.agent.turn_log: инсайт за 4.1 с
… INFO [f0eb…/9940…] app.core.agent.turn_log: график bar за 0.1 с
… INFO [f0eb…/9940…] app.core.agent.turn_log: итог хода: ok за 7.5 с
```

- Маршрут: `small talk`, `обзор таблицы`, `смена вида графика`, `план` или
  `ответ на уточнение`.
- Итог хода — одна строка: `ok`, `failed`, `clarification` или `disconnected`
  (клиент закрыл поток), общее время, а для неуспешного хода — этап (`start`,
  `planning`, `step N`, `insight`, `chart`) и причина. `failed` и `disconnected` —
  на уровне WARNING.
- Вызов LLM: модель, схема ответа, время, `prompt_tokens` и длина ответа. Сбой —
  тип (таймаут, соединение, `HTTP <код>`), адрес сервера без логина и пароля и
  сколько ждали.
- При старте — одна строка `старт:` с моделью, адресом LLM, structured mode,
  контекстом, таймаутом и путём к файлу логов; ключи и DSN не пишутся.

Уровень задаёт `LOG_LEVEL` (`DEBUG`, `INFO` — по умолчанию, `WARNING`, `ERROR`).
На `DEBUG` в лог идут промпты и ответы модели целиком; на `INFO` их нет. httpx,
openai и instructor всегда на WARNING. В логе есть вопросы пользователей, поэтому
он хранится только локально в `storage/`.

Найти ход: `turn_id` приходит фронту в событии `done` (и `clarification_needed`).

```bash
docker compose logs backend | grep <turn_id>
grep <turn_id> backend/storage/logs/backend.log*
grep 'итог хода: failed' backend/storage/logs/backend.log   # все упавшие ходы
```

## Требования к железу и выбор модели

<!-- TODO(#58): заменить модели и цифры итогами выбора по eval (docs/reports/llm_choice.md). -->

| Режим | Команда | Модель по умолчанию | Память под модель* | Диск |
|---|---|---|---|---|
| CPU | `make up` | `qwen2.5-coder:7b` (`LLM_MODEL`) | ≈ 6 ГБ RAM | ≈ 5 ГБ |
| GPU NVIDIA | `make up-gpu` | `qwen2.5-coder:14b` (`LLM_MODEL_GPU`) | ≈ 12 ГБ VRAM | ≈ 9 ГБ |

\* Веса модели в 4-битной квантизации плюс кеш контекста на 16 тыс. токенов
(`OLLAMA_CONTEXT_LENGTH`). Ориентировочные оценки, замеры — в отчёте о выборе
модели. Сама платформа (backend, frontend, DuckDB) занимает ещё около 2 ГБ RAM и
4 ГБ диска под образы.

- **Рекомендуется:** 16 ГБ RAM и 4+ ядра для CPU-режима; на CPU ответ занимает
  десятки секунд, на GPU — секунды.
- **Слабая машина:** в `.env` можно поставить `LLM_MODEL=qwen2.5-coder:1.5b`
  (≈ 1 ГБ) — работает быстрее, но планирует заметно хуже.
- **Другая модель:** любая модель из библиотеки Ollama — достаточно поменять
  `LLM_MODEL` в `.env` и выполнить `make up`; она скачается при старте.

## Данные

- **CSV:** кнопка загрузки в интерфейсе. Кодировка (UTF-8 или cp1251),
  разделитель и числа вида «1 234,56» распознаются автоматически; файл до
  1 ГБ (`CSV_MAX_UPLOAD_MB`). К файлу можно приложить описание данных (README,
  словарь колонок) — из него в паспорт таблицы попадут названия и описания колонок.
- **PostgreSQL:** форма подключения в интерфейсе, строка вида
  `postgresql://user:password@host:5432/dbname`. Подключение только на чтение;
  после перезапуска источник восстанавливается сам, пароль берётся из
  `POSTGRES_PASSWORD` в `.env` (на диск он не пишется).

## Ограничения

<!-- TODO(#81): сверить список после bug bash. -->

- Один пользователь на экземпляр: авторизации нет, рассчитано на локальный запуск.
- Качество ответов зависит от модели: маленькие модели (1.5b–3b) чаще ошибаются
  в плане и просят уточнения.
- На CPU ответ на сложный вопрос — до минуты и дольше.
- GPU-режим — только NVIDIA (`make up-gpu`); на AMD и Apple модель работает на CPU.
- PostgreSQL: из схемы подключается до 50 таблиц (`POSTGRES_MAX_TABLES`); параметры
  строки подключения кроме хоста, порта, базы и пользователя (например `sslmode`)
  после перезапуска не восстанавливаются.
- Код, который пишет агент, выполняется в WASM-песочнице без сети, с лимитами
  60 с и 2 ГБ на запуск (`WASM_TIMEOUT_S`, `WASM_MEM_MB`).
